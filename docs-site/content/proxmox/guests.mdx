# Guests maken en weghalen

Een extra machine op pve01 maken, of er een weghalen: een container (LXC),
een OCI-container of een virtuele machine (VM).

Twijfel je tussen container en VM? Kies de **container**. Die start in een
seconde, kost bijna geen geheugen, en alles gaat automatisch. Een VM is voor als
het echt niet anders kan, bv. een eigen besturingssysteem zoals Home Assistant OS.

<Callout type="info">
Wil je gewoon een **Docker-app** draaien (Memos, Jellyfin…)? Dan heb je **geen
nieuwe machine** nodig. Zie [Dienst toevoegen](/docker/toevoegen/).
</Callout>

## Welk geval ben jij?

| Jouw situatie | Voorbeeld | Ga naar |
| --- | --- | --- |
| Je wil een **nieuwe container** voor software die een eigen machine hoort te hebben | Vaultwarden op een eigen LXC | [Nieuwe container](#een-nieuwe-container) |
| Je wil **één programma uit een Docker-image** dat moet blijven werken als de docker-VM plat ligt | `ntfy` | [OCI-container](#een-oci-container) |
| Je hebt echt een **virtuele machine** nodig (eigen kernel, eigen OS) | zoals `haos` of `docker` | [Virtuele machine](#een-virtuele-machine) |
| Je container of VM staat er en heeft de baseline | `vaultwarden` na het bouwen | [Afwerken](#afwerken) |
| Een machine heeft **meer geheugen, cores of schijf** nodig | `docker` krijgt 20 GB in plaats van 16 | [Machine aanpassen](#een-machine-aanpassen) |
| Een **container of VM** op pve01 mag weg | een test-LXC | [Machine weghalen](#een-machine-weghalen) |
| Je wil weten welke guests er echt draaien, of het API-token nog werkt | Ansible ziet een host niet | [Guests en API-token checken](#guests-en-api-token-checken) |
| Na een herbouw starten guests **niet mee op** als pve01 opstart | na een restore staat de helft op `onboot: 0` | [Guests mee laten opstarten](#guests-mee-laten-opstarten) |

## Een nieuwe container

Voorbeeld: Vaultwarden op een eigen LXC. Alles gebeurt vanaf je werkstation,
het Proxmox-scherm heb je niet nodig. **OpenTofu** maakt de container (zie
[OpenTofu](/opentofu/)), daarna zet Ansible hem klaar.

<Steps>

#### Zoek een vrij nummer

```bash
ssh pve01 'sudo pvesh get /cluster/resources --type vm'   # elke guest: vmid, naam, status
```

Kies een nummer dat daar niet in staat.

<Callout type="warning">
Neem **niet** `109` of `110`: daar staan nog oude back-ups van in PBS, en een
nieuwe guest met dat nummer komt in dezelfde back-upgroep terecht. `199` is
gereserveerd voor de restore-drill.
</Callout>

#### Zoek een vrij adres

Kijk in `tofu/proxmox/containers.tf` welke adressen al gebruikt worden, en
test of het adres echt vrij is:

```bash
ping -c 2 192.168.0.31   # geen antwoord = waarschijnlijk vrij
```

#### Zet de container in `containers.tf`

```bash
$EDITOR tofu/proxmox/containers.tf
```

Voeg in `local.containers` een blok toe, naast de andere:

```hcl
    vaultwarden = {
      vm_id        = 111
      cores        = 1
      memory       = 512
      swap         = 512
      disk         = { datastore = "vm-hdd", size = 8 }
      ip           = "192.168.0.31/24"
      ipv6_auto    = false
      mac          = null
      keyctl       = false
      dns_servers  = ["192.168.0.29"]
      searchdomain = "home.arpa"
      tags         = []
    }
```

| Veld | Wat je invult |
| --- | --- |
| de naam (`vaultwarden`) | kleine letters, geen spaties. Wordt ook zijn naam in de inventory |
| `vm_id` | het vrije nummer |
| `cores` / `memory` / `swap` | geheugen in MB. Begin klein, ophogen kan later |
| `disk` | opslag + grootte in GB. `vm-hdd` voor gewone dingen, `local-lvm` als het snel moet |
| `ip` | het vrije adres, met `/24` erachter |
| `mac` | `null`: dan kiest Proxmox er een. Zet hem na het bouwen vast (zie hieronder) |
| `dns_servers` / `searchdomain` | zoals hierboven: AdGuard als DNS, `home.arpa` als zoekdomein |

Gateway, template en de Ansible-sleutel staan één keer onderaan hetzelfde
bestand. Die hoef je niet in te vullen.

#### Kijk wat OpenTofu gaat doen

```bash
bin/tofu proxmox plan
```

Onderaan moet `1 to add, 0 to change, 0 to destroy` staan. Staat er iets
anders, stop en kijk eerst wat er nog verandert.

#### Maak de container

```bash
bin/tofu proxmox apply
```

Hij toont het plan nog een keer; typ `yes`. De container staat er nu, met de
Ansible-sleutel in root.

#### Zet hem klaar met Ansible

```bash
ansible-playbook playbooks/new-guest.yml -e guest=vaultwarden
```

Dit wacht tot SSH luistert, vertrouwt zijn hostkey, zet het `ansible`-account
erop en past de baseline toe. Aan het eind staat in beeld wat je hierna doet.

#### Zet het MAC-adres vast

Proxmox koos een MAC. Kijk welk, zet het in plaats van `null` bij `mac`, en
draai `bin/tofu proxmox plan`: dat moet nu `No changes` zeggen. Zo krijgt
een herbouw hetzelfde MAC, en dus hetzelfde adres in UniFi.

```bash
ssh pve01 'sudo pct config 111 | grep net0'   # hwaddr=BC:24:11:...
```

#### Commit en push

```bash
git add tofu/proxmox/containers.tf
git commit -m "feat: vaultwarden container"
git push
```

#### Werk de container af

De machine staat er, maar is nog leeg. Ga verder met
[Afwerken](#afwerken).

</Steps>

## Een OCI-container

Sinds Proxmox 9.1 kan een Docker-image rechtstreeks een container worden,
zonder Docker ertussen. Er zit geen Debian in, geen SSH en geen apt: alleen
het programma. Proxmox noemt dit nog een tech preview.

**Wanneer wel:** voor iets kleins dat moet blijven werken als de docker-VM
plat ligt. `ntfy` is het voorbeeld: wie meldt dat de docker-VM stuk is, mag er
niet zelf op draaien.

**Wanneer niet:** voor al de rest. Iets met meerdere containers (Immich), of
iets waarvan de data belangrijk is, hoort op de docker-host. Daar heb je
compose, healthchecks en `docker compose pull`.

<Steps>

#### Zet hem in `pve_oci_lxcs`

In `inventory/group_vars/proxmox/lxcs.yml`, met een vaste `version`, nooit
`latest`. Kijk naar `ntfy` als voorbeeld. Twee dingen die je bij een nieuw
image moet nakijken:

- **`entrypoint`**: veel images hebben een `ENTRYPOINT` zonder argumenten.
  Kaal start dat de help en stopt meteen, zonder melding.
- **`volumes`**: elke map waar het programma naar schrijft en die niet in het
  image zit. Ontbreekt er een, dan stopt de container.

Zet alles wat moet blijven bestaan in `env`, niet op de schijf. Zie
[Updaten is opnieuw bouwen](#updaten-is-opnieuw-bouwen).

#### Bouw de OCI-container

```bash
ansible-playbook playbooks/proxmox-oci.yml
```

De rol haalt het image op, maakt de container, zet `entrypoint` en `env`, en
start hem. Een tweede run doet niets.

#### Geef hem een naam (optioneel)

Zoals bij een gewone container, in `caddy_sites`: zie
[Afwerken → Geef hem een adres](#geef-hem-een-adres-optioneel).
Geef hem een vaste `upstream` in plaats van alleen `host`: een gestopte
OCI-container heeft geen adres in de inventory, en dan faalt de Caddyfile
voor elke site. De container staat na de eerste run in de inventory, onder
`appliances`.

</Steps>

### Waarom anders dan een gewone container

- **Geen `new-guest.yml`**: er is geen SSH, dus geen bootstrap en geen
  baseline. De tag `oci` houdt hem buiten `linux`, anders zou `site.yml` er
  vergeefs de baseline op proberen.
- **Proxmox negeert `entrypoint` en `env` bij het aanmaken** en neemt die van
  het image over. Daarom zet de rol ze er achteraf op, en herstart hij de
  container als ze veranderen: env wordt alleen bij het starten gelezen.
- **`env` gaat via de API, niet via `pct`**: Proxmox wil de variabelen
  gescheiden door NUL-tekens, en een shell kan die niet doorgeven. Alles plakt
  dan aan elkaar, `PATH` verdwijnt, en de container stopt zonder uitleg. Wie
  `env` zet, vervangt trouwens alles, ook de `PATH` van het image; de rol zet
  die daarom altijd zelf mee.
- **Het image ophalen gebeurt als root**, alles daarna met de API-token van
  Ansible. Ophalen vraagt het recht om pve01 van eender waar te laten
  downloaden, en dat hoort die token niet te hebben voor één `pull`.

### Updaten is opnieuw bouwen

Een OCI-container kun je niet `apt upgrade`n: je hoogt `version` op en bouwt
hem opnieuw. Dat sloopt de container **en zijn volumes**, daarom staat alles
wat moet overleven in `env`. Voor ntfy zijn dat de gebruikers, rechten en
tokens; je verliest alleen de berichtcache van de laatste uren.

De stappen staan in [Updates → OCI-containers](/proxmox/onderhoud/#oci-containers).

### ntfy op je iPhone

Installeer de app **ntfy**. Onder Instellingen → Standaardserver:
`https://ntfy.neodata.be`, gebruiker `ruben`. Het wachtwoord staat in de vault:

```bash
ansible-vault view inventory/group_vars/proxmox/vault.yml | grep ntfy_ruben_password
```

Abonneer op het topic `homelab`. Proxmox en PBS sturen daar hun
waarschuwingen en fouten heen, elk met een eigen token (een mislukte back-up bijvoorbeeld), rechtstreeks naar
`192.168.0.32` en dus niet via Caddy: een melding over een storing mag niet
afhangen van Caddy of AdGuard. Geslaagde back-ups komen er bewust niet: wie
elke nacht een "OK" krijgt, leest de ene "failed" niet meer.

Een mislukte back-up stuurt de hele log mee, en dat is al snel meer dan de
4 KB die in één bericht past. Die komt binnen als "You received a file:
attachment.txt": de titel zegt wat er misging, de bijlage is de log. Daarvoor
staat `NTFY_ATTACHMENT_CACHE_DIR` in de env; zonder weigert ntfy zo'n bericht
en krijg je niets.

Buitenshuis zonder VPN krijg je wel het seintje, maar kan de app de inhoud
niet ophalen. `ntfy.neodata.be` is alleen thuis of via de VPN bereikbaar.

## Een virtuele machine

OpenTofu maakt de lege VM, uit een blok in `tofu/proxmox/vms.tf`. Debian
installeren doe je **met de hand** in de console
([waarom](#waarom-vms-niet-automatisch)). Daarna neemt Ansible het over, net
als bij een container.

Voorbeeld: een VM `nieuwehost` met Debian.

### Het grote plaatje

| Stap | Waar | Wat |
| --- | --- | --- |
| 1 | Proxmox-scherm | Debian-ISO ophalen |
| 2 | je werkstation | blok in `vms.tf`, `bin/tofu proxmox apply` |
| 3 | Proxmox-console | Debian installeren |
| 4 | in de VM | guest agent aanzetten |
| 5 | UniFi | adres vastzetten |
| 6–8 | je werkstation | Ansible hem laten zien, sleutel erop, `bootstrap` + `baseline` |
| 9 | je werkstation | MAC vastzetten, commit en push |

<Callout type="info">
Bouw je een **vervanger** van een bestaande VM (bv. `docker`)? Dan maak je
geen nieuwe VM: je zet een back-up terug uit PBS, zie
[Herstellen](/proxmox/herstellen/). Zijn vorm (cores, geheugen, schijf en
vooral het **MAC-adres**, waar zijn vaste adres in UniFi aan hangt) staat al
in `tofu/proxmox/vms.tf`.
</Callout>

<Steps>

#### Haal de Debian-installer op

Eén keer; staat hij er al, sla dit over.

1. Open het Proxmox-scherm: `https://192.168.0.10:8006`.
2. Links: **pve01 → local (pve01) → ISO Images → Download from URL**.
3. Plak de link naar het nieuwste `debian-…-amd64-netinst.iso` van
   [cdimage.debian.org/debian-cd/current/amd64/iso-cd](https://cdimage.debian.org/debian-cd/current/amd64/iso-cd/)
   en klik **Query URL**, dan **Download**.

#### Maak de VM aan

Kies een vrij nummer en een naam zoals bij
[een container](#zoek-een-vrij-nummer). Zet dan een blok onderaan
`tofu/proxmox/vms.tf`:

```hcl
resource "proxmox_virtual_environment_vm" "nieuwehost" {
  node_name     = local.node
  vm_id         = 112
  name          = "nieuwehost"
  on_boot       = true
  bios          = "ovmf"
  machine       = "q35"
  scsi_hardware = "virtio-scsi-single"
  boot_order    = ["scsi0", "ide2"]

  agent {
    enabled = true
  }

  cpu {
    cores = 2
    type  = "host"
  }

  memory {
    dedicated = 2048
  }

  efi_disk {
    datastore_id = "vm-hdd"
  }

  disk {
    interface    = "scsi0"
    datastore_id = "vm-hdd"
    size         = 32
    discard      = "on"
    ssd          = true
  }

  cdrom {
    interface = "ide2"
    file_id   = "local:iso/debian-13.1.0-amd64-netinst.iso"
  }

  network_device {
    bridge = "vmbr0"
    model  = "virtio"
  }

  operating_system {
    type = "l26"
  }

  lifecycle {
    prevent_destroy = true
  }
}
```

| Veld | Waarom |
| --- | --- |
| `"nieuwehost"` en `name` | wordt zijn naam in de inventory: kleine letters, geen spaties |
| `on_boot` | komt terug na een herstart van pve01 |
| `agent` | **aan**: zonder vindt Ansible zijn adres niet |
| `cpu.type = "host"` | volle snelheid van de processor |
| `memory` | in MB. Zie [hoeveel geheugen](#hoeveel-geheugen-een-vm-krijgt) |
| `disk.size` | in GB, groter maken kan later. `discard` geeft vrije ruimte terug aan de opslag |
| `cdrom.file_id` | het ISO uit de vorige stap, precies zoals Proxmox het noemt |
| `prevent_destroy` | OpenTofu mag hem nooit weggooien |

```bash
bin/tofu proxmox plan    # moet eindigen op "1 to add"
bin/tofu proxmox apply   # typ yes
```

Selecteer de VM daarna in het Proxmox-scherm en klik **Start**, dan
**Console**.

#### Installeer Debian

In de console kies je **Install** (niet Graphical install) en volg je de
vragen. Alleen deze zijn belangrijk:

| Vraag | Antwoord | Waarom |
| --- | --- | --- |
| Netwerk | laat DHCP zijn werk doen | het adres zet je straks vast in UniFi |
| Hostname | `nieuwehost` | dezelfde naam als de VM |
| Domain name | leeg | |
| Root password | **leeg laten** (twee keer Enter) | dan krijgt de gebruiker hieronder `sudo`, en dat heeft Ansible straks nodig |
| Gebruiker | bv. `ruben` + wachtwoord | alleen voor de eerste keer, daarna gebruikt Ansible zijn eigen account |
| Partitioning | Guided – use entire disk, alles op één partitie | |
| Software selection | **alleen** SSH server + standard system utilities | geen desktop |

Na de herstart log je in de console in met je gebruiker.

#### Zet de guest agent aan

In de VM:

```bash
sudo apt install -y qemu-guest-agent
sudo systemctl enable --now qemu-guest-agent
ip -4 addr show   # onthoud het adres, bv. 192.168.0.99
```

De guest agent vertelt Proxmox het adres van de VM. Via die weg vindt Ansible
hem: een VM zet je **nooit** met de hand in de inventory.

#### Zet zijn adres vast in UniFi

In UniFi: zoek het toestel `nieuwehost` bij de clients en zet **Fixed IP** aan
op het adres dat hij nu heeft. Zo krijgt hij na een herstart hetzelfde adres,
en blijven routes in Caddy kloppen.

#### Controleer dat Ansible hem ziet

Terug op je werkstation:

```bash
ansible-inventory --host nieuwehost | grep ansible_host
```

Zie je `"ansible_host": "192.168.0.99"`, dan is het goed. Niets? Kijk in het
Proxmox-scherm bij de VM → **Summary**: staat bij IPs "Guest Agent not
running", dan is stap 4 of het vinkje **Qemu Agent** niet gelukt (dat vinkje
vraagt een volledige stop en start van de VM, geen reboot van binnenuit).

#### Zet de Ansible-sleutel op je gebruiker

```bash
ssh-copy-id -i ~/.ssh/ansible_ed25519.pub ruben@192.168.0.99
```

Hij vraagt eerst of je de hostkey vertrouwt (`yes`), dan het wachtwoord van
`ruben`. Daarna kan Ansible zonder wachtwoord binnen.

#### Zet het ansible-account erop en pas de baseline toe

```bash
ansible-playbook playbooks/bootstrap.yml --limit nieuwehost -u ruben -K
ansible-playbook playbooks/baseline.yml --limit nieuwehost
```

`-u ruben` logt de eerste keer in als jouw gebruiker, `-K` vraagt zijn
sudo-wachtwoord. `bootstrap` maakt het `ansible`-account; vanaf `baseline`
gebruikt alles dat account.

#### Zet het MAC-adres vast en commit

Proxmox koos een MAC. Kijk welk, en zet het als `mac_address` in het
`network_device`-blok:

```bash
ssh pve01 'sudo qm config 112 | grep net0'   # virtio=BC:24:11:...
bin/tofu proxmox plan                         # moet "No changes" zeggen
git add tofu/proxmox/vms.tf
git commit -m "feat: nieuwehost VM"
git push
```

Aan dat MAC hangt zijn vaste adres in UniFi. Staat het vast, dan krijgt een
herbouw hetzelfde adres.

#### Werk de VM af

Ga verder met [Afwerken](#afwerken).

</Steps>

## Afwerken

Je machine staat er en heeft de baseline, via
[Nieuwe container](#een-nieuwe-container) of
[Virtuele machine](#een-virtuele-machine). Nu zet je er iets op
en zorg je dat hij overal meetelt. Voorbeeld: `vaultwarden`.

<Steps>

#### Installeer de dienst

Voor software zonder Docker schrijf je een rol. Dat staat in
[Dienst toevoegen → Eigen rol](/ansible/rol/#een-eigen-rol-zonder-docker).

#### Geef hem een adres (optioneel)

Wil je hem op `https://vaultwarden.neodata.be`, zet dan een route in
`inventory/host_vars/caddy/main.yml` onder `caddy_sites`:

```yaml
  - { name: vaultwarden, host: vaultwarden, port: 8080, desc: "Wachtwoordkluis" }
```

```bash
ansible-playbook playbooks/caddy.yml
ansible-playbook playbooks/smoketest.yml --tags caddy
```

Alle velden van een route: zie [Dienst toevoegen → Alleen een adres](/netwerk/caddy/#alle-velden-van-een-route).

#### Zet hem in de wekelijkse back-up

De dagelijkse back-up naar PBS neemt elke guest vanzelf mee. De wekelijkse
kopie naar de Mac mini **niet**: die heeft een vaste lijst.

```bash
$EDITOR inventory/group_vars/proxmox/backup.yml   # vmid toevoegen aan "101,102,…,108"
ansible-playbook playbooks/proxmox-datacenter.yml
```

#### Commit en push

```bash
git add inventory/ roles/ playbooks/
git commit -m "vaultwarden erbij"
git push
```

<Callout type="error">
Sla dit niet over. Semaphore draait zijn geplande runs vanuit git, niet vanaf
je laptop. Een route of rol die niet gepusht is, bestaat voor Semaphore niet
en kan bij de volgende run weer verdwijnen.
</Callout>

#### Controleer

```bash
ansible-playbook playbooks/site.yml --check --diff --limit vaultwarden
```

Verandert niets, toont alleen wat er nog zou veranderen. Staat er niets open,
dan klopt alles.

#### Werk de docs bij

```bash
ansible-playbook playbooks/docs.yml
```

De pagina's met hosts en containers op deze site worden uit de inventory
gemaakt. Zonder deze stap staat je nieuwe machine er niet op.

</Steps>

## Als het misgaat

| Wat je ziet | Wat het is |
| --- | --- |
| `new-guest.yml` stopt meteen met een lijst namen | Proxmox kent die naam niet: de container bestaat nog niet. Zet hem in `tofu/proxmox/containers.tf`, draai `bin/tofu proxmox apply` en dan opnieuw |
| `bin/tofu proxmox plan` zegt `must be replaced` | OpenTofu wil de machine weggooien en leeg opnieuw maken. **Nooit** `apply` doen. Meestal staat er een veld in de `.tf` dat Proxmox anders heeft (template, opslag). `prevent_destroy` houdt het tegen, maar zoek de oorzaak |
| `bin/tofu proxmox plan` wil iets terugzetten dat je in het Proxmox-scherm veranderde | Het `.tf`-bestand wint. Zet de waarde daar, zie [Machine aanpassen](#een-machine-aanpassen) |
| Het blijft hangen bij "Wait for SSH" (3 minuten) | De container start niet, of het adres klopt niet. Kijk in het Proxmox-scherm of hij draait en welk adres hij heeft |
| Een fout over een hostkey | Er stond al een andere machine op dat adres. `ssh-keygen -R <adres>` en opnieuw |
| Een fout over het vault-wachtwoord | `~/.ansible/vault_pass_infra` ontbreekt of klopt niet. Zie de README |
| Een VM staat niet in de inventory | De guest agent draait niet. Zie [Virtuele machine](#controleer-dat-ansible-hem-ziet) |
| Een OCI-container staat meteen weer op `stopped` | Meestal een ontbrekend `entrypoint`-argument of een map die niet bestaat. Zet `lxc.console.logfile: /tmp/ct.log` onderaan `/etc/pve/lxc/<vmid>.conf`, start hem, en lees dat bestand. Haal de regel daarna weer weg |

Een half klaargezette container is niet erg: `new-guest.yml` mag altijd
opnieuw. Wat al klaarstaat wordt niet nog eens gedaan.

## Een machine aanpassen

Een container of VM heeft meer geheugen, cores of schijf nodig. Voorbeeld:
`docker` krijgt 20 GB geheugen in plaats van 16. Dat doe je in het
`.tf`-bestand, **niet** in het Proxmox-scherm: het volgende plan zou je
wijziging daar weer terugdraaien.

<Steps>

#### Pas het getal aan

```bash
$EDITOR tofu/proxmox/vms.tf          # een VM: zijn eigen blok
$EDITOR tofu/proxmox/containers.tf   # een container: zijn regel in local.containers
```

Bij `docker`: `dedicated = 16384` wordt `dedicated = 20480` (in MB).

#### Kijk wat OpenTofu gaat doen

```bash
bin/tofu proxmox plan
```

Alleen jouw veld mag veranderen, met `update in-place` erbij, en onderaan
`0 to add, 1 to change, 0 to destroy`. Staat er `must be replaced`: stop,
nooit `apply`. Dat betekent een lege schijf.

#### Voer het uit

```bash
bin/tofu proxmox apply   # typ yes
```

Een container krijgt het meteen. Een VM krijgt nieuw geheugen of cores pas na
een herstart: `ssh pve01 sudo qm reboot <vmid>` (alle diensten erop gaan even
plat).

#### Commit en push

```bash
git add tofu/proxmox/
git commit -m "chore: docker 20 GB geheugen"
git push
```

#### Werk de docs bij

```bash
ansible-playbook playbooks/docs.yml
```

De pagina [Machines](/homelab/machines/) leest cores, geheugen en schijf live
uit Proxmox, en staat daarna ook goed.

</Steps>

<Callout type="warning">
Een schijf kan alleen **groter**. Een kleiner getal zet OpenTofu niet door:
het plan wil de machine dan vervangen, en dat mag nooit.
</Callout>

## Een machine weghalen

Een container (LXC of OCI) of VM op pve01.

<Steps>

#### Haal eerst alles erop weg

Elke route naar deze machine, en elke stack erop: zie de twee gevallen
hierboven. Anders wijst `unifi-routes.yml` elke ochtend naar een adres dat
niet meer bestaat.

#### Maak een back-up als je twijfelt

Proxmox → de guest → **Backup** → **Backup now**, naar `pbs`. Zo kan je hem
nog terugzetten als je je vergist.

#### Vernietig hem in Proxmox

Met de hand: Proxmox → de guest → **More** → **Remove**, met **Purge** aan. Of
als root op pve01:

```bash
pct destroy <vmid> --purge   # container
qm destroy <vmid> --purge    # VM
```

Geen playbook en geen `bin/tofu` doet dit, met opzet: elke guest heeft
`prevent_destroy`. Een typfout mag geen machine kosten.

#### Laat OpenTofu hem vergeten

Sla dit over voor een OCI-container (ntfy): die staat niet in OpenTofu.

```bash
bin/tofu proxmox state list                                           # zoek zijn adres
bin/tofu proxmox state rm 'proxmox_virtual_environment_container.this["vaultwarden"]'
```

Een VM heet bv. `proxmox_virtual_environment_vm.docker`. Haal daarna zijn
regel uit `local.containers` in `tofu/proxmox/containers.tf`, of zijn blok uit
`tofu/proxmox/vms.tf`.

```bash
bin/tofu proxmox plan   # moet "No changes" zeggen
```

#### Haal hem uit de lijsten

| Bestand | Wat |
| --- | --- |
| `inventory/group_vars/proxmox/lxcs.yml` | alleen voor een OCI-container: zijn item in `pve_oci_lxcs` |
| `inventory/group_vars/proxmox/backup.yml` | zijn vmid in de wekelijkse job naar de Mac mini (de PBS-job neemt `all` en past zich zelf aan) |
| `inventory/group_vars/all/unifi.yml` | zijn MAC in `unifi_known_macs` |

#### Ruim op buiten git

| Waar | Wat |
| --- | --- |
| UniFi → Client Devices | Fixed IP en alias van de machine |
| Tailscale → Machines | de node, als hij op de tailnet zat |

#### Laat de rest zich aanpassen

```bash
ansible-playbook playbooks/adguard.yml   # haalt <naam>.home.arpa weg
ansible-playbook playbooks/docs.yml      # haalt hem van de pagina Machines
git add -A && git commit -m "chore: remove <naam>" && git push
```

De Proxmox-inventory vindt hem vanzelf niet meer. `adguard.yml` haalt elke
naam weg die niet meer in de inventory staat.

</Steps>

## Guests mee laten opstarten

Na een herbouw of restore starten guests niet mee op als pve01 opstart: ze
staan op `onboot: 0`.

<Steps>

#### Bedenk welke guests níét mogen meestarten

Het playbook zet `onboot` aan op **elke** guest die het uit heeft staan, ook op
een guest die je bewust uit liet.

#### Draai het playbook

```bash
ansible-playbook playbooks/proxmox-autostart.yml
```

De uitvoer toont per aangepaste guest `<vmid> <naam>`.

#### Zet de uitzonderingen terug uit

```bash
ssh pve01 sudo pct set <vmid> --onboot 0    # voor een LXC
ssh pve01 sudo qm set <vmid> --onboot 0     # voor een VM
```

</Steps>

<Callout type="warning">
De guests uit `tofu/proxmox/` (100–108) staan daar op meestarten
(`on_boot` / `start_on_boot = true`). Zet je er een met de hand uit, dan wil
het volgende `bin/tofu proxmox plan` hem weer aanzetten. Moet er een echt uit
blijven, verander het dan in het `.tf`-bestand.
</Callout>

<Callout type="info">
Waarom dit niet in `site.yml` zit: zie
[Goed om te weten](#waarom-proxmox-autostartyml-niet-in-siteyml-zit).
</Callout>

## Guests en API-token checken

Ansible ziet een host niet? Kijk eerst of Proxmox hem kent, en of het
API-token nog werkt.

<Steps>

#### Vraag de inventory op

```bash
ansible-inventory --graph
```

De guests komen uit `homelab.proxmox.yml`, via het API-token. Zie je alleen
`pve01` en de Macs, dan werkt het token niet (of ontbreekt `proxmoxer`, zie
[Laptop](/ansible/laptop/#laptop-klaarzetten)). Dát is dan je probleem, niet de host
die je zocht.

#### Vraag Proxmox zelf

```bash
ssh pve01 'sudo pvesh get /cluster/resources --type vm'
```

Toont elke guest met vmid, naam en status, ook als het token stuk is. Staat
hij hier wel en in de inventory niet, dan ligt het aan het token.

</Steps>

## Goed om te weten

### Waar het adres van een container vandaan komt

Het adres staat in `tofu/proxmox/containers.tf`; OpenTofu zet het bij het
maken op de container. Daarna haalt de inventory het live uit Proxmox. Je
schrijft het adres dus nergens anders op, en zet een guest **nooit** in
`00-static.yml`: dat overschaduwt de live gegevens.

### Waarom OpenTofu voor de machines

OpenTofu onthoudt wat het gemaakt heeft, en toont eerst een plan: wat erbij
komt, wat verandert, wat weg zou gaan. Pas na `yes` gebeurt er iets.

Vroeger maakte Ansible de containers. Dat maakte alleen wat ontbrak, en raakte
een bestaande guest nooit aan. Zette je `memory` hoger in de lijst, dan
gebeurde er niets, en liepen lijst en werkelijkheid stilletjes uit elkaar.
Nu toont elk plan zo'n verschil meteen.

De taakverdeling: **PBS bewaart de inhoud** (de schijf), **OpenTofu de vorm**
(cores, geheugen, schijfgrootte, adres, MAC). Samen krijg je een guest precies
terug.

### Hoeveel geheugen een VM krijgt

Geef een VM wat zijn diensten echt gebruiken, plus wat ruimte voor pieken, en
niet "zoveel als er vrij is". Linux vult elk vrij geheugen in de VM met
bestandscache. Zonder balloon geeft een VM dat nooit terug, dus voor pve01 is
het gewoon bezet.

De `docker`-VM had tot 23-09 28 GB. Proxmox zag 26 GB in gebruik, maar de
containers zelf gebruikten er samen maar ~4,2 GB van. De rest was cache. Op
pve01 bleef daardoor maar ~9 GB over voor alle andere guests en de ZFS-cache.
Nu heeft hij 16 GB, genoeg voor de pieken van Immich.

Wat een VM echt gebruikt, zie je **binnen** de VM, niet in Proxmox:

```bash
free -m                   # kijk naar "used", niet naar "buff/cache"
docker stats --no-stream  # per container
```

Aanpassen doe je in `tofu/proxmox/vms.tf`, zie
[Machine aanpassen](#een-machine-aanpassen). Het gaat pas in na een herstart:

```bash
ssh pve01 sudo qm pending <vmid>   # toont wat er nog wacht
ssh pve01 sudo qm reboot <vmid>    # herstart hem netjes, alle diensten erop gaan even plat
```

### Waarom de hostkey via Proxmox gelezen wordt

Een nieuwe container heeft een hostkey die niemand kent, en Ansible kan die
niet zomaar accepteren. `new-guest.yml` leest de sleutel via `pct exec`
rechtstreeks van de schijf van de container. Zo vertrouw je de echte machine,
en niet wat er toevallig op dat adres antwoordt.

### Waarom VM's niet automatisch

Een VM ontleent zijn waarde aan wat er op zijn schijf staat, niet aan zijn
instellingen. OpenTofu maakt de lege machine met de juiste vorm, maar het
besturingssysteem erop installeren doe je één keer met de hand: elke VM is
anders (Home Assistant OS, PBS, Debian). Een bestaande VM kwijt? Dan maak je
hem niet opnieuw, je zet een back-up terug uit PBS. `tofu/proxmox/vms.tf`
houdt daarna zijn vorm juist.

### Waarom `proxmox-autostart.yml` niet in `site.yml` zit

Een guest die bewust níét meestart, zou bij elke run stilletjes weer aangezet
worden. Meestal draai je dit één keer, na een herbouw.
