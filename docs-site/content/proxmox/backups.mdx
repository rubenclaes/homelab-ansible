# Back-ups

Waar de back-ups staan, wat je **nu al** moet doen zodat terugzetten later
lukt, en hoe je test dat terugzetten echt werkt.

## Vooraf: doe dit nu

Doe dit terwijl alles nog werkt. Achteraf kan het niet meer.

<Steps>

#### Maak een papieren kopie van de PBS-sleutel

```bash filename="laptop"
ssh pve01
```

```bash filename="pve01"
sudo ls /etc/pve/priv/storage/                                         # hier hoort pbs.enc te staan
sudo proxmox-backup-client key paperkey /etc/pve/priv/storage/pbs.enc --output-format text
```

Print wat eruit komt, en bewaar het **buiten het huis** (bv. ook in de
wachtwoordkluis). Zonder deze sleutel zijn de back-ups op PBS niet terug te
zetten.

Doe hetzelfde met de sleutel van `docker` (app-data en foto's, sinds 25-09):

```bash filename="laptop"
ssh docker 'sudo proxmox-backup-client key paperkey /root/.config/proxmox-backup/docker-data.key --output-format text'
```

**Let op:** Vaultwarden draait zelf in de homelab. Brandt het huis af, dan is Vaultwarden
ook weg, en zit hij in R2 achter precies deze sleutels. **Papier** is dus het
echte vangnet: sleutels en vault-wachtwoorden samen, liefst ook een kopie
buiten het huis.

**Let op:** `proxmox-backup-client key show` toont alleen de vingerafdruk van de sleutel,
niet de sleutel zelf. Daar kan je niets mee terugzetten.

#### Bewaar de twee vault-wachtwoorden op dezelfde plek

```bash filename="laptop"
cat ~/.ansible/vault_pass_infra
cat ~/.ansible/vault_pass_stacks
```

Ze openen alles wat de repo versleuteld bewaart: API-tokens, logins, de
`.env`-bestanden van de stacks. Ze staan niet in git, met opzet.

<Callout type="error">
Kwijt = de repo is compleet maar onbruikbaar. Bijna elk playbook leest een
vault-bestand. Ze zijn nergens uit af te leiden: de enige weg terug is elk
vault-bestand opnieuw maken en elk secret opnieuw zetten.
</Callout>

</Steps>

## Herstellen testen

### Af en toe: bewijs dat herstellen werkt

Een herstelpad dat nooit gedraaid heeft, is een aanname.

```bash filename="laptop"
ansible-playbook playbooks/restore-drill.yml -e drill_confirm=true
```

Bewijst dat je je **data** terugkrijgt uit PBS: de sleutel werkt en het archief
is heel. Draait vanzelf op de 1e van de maand; met de hand na wijzigingen aan
de back-upjobs.

Hij zet de back-up terug op vmid 199 en sloopt die op het eind.

**Faalt de drill, dan blijft 199 staan**, zodat je kan kijken wat er misging.
Opruimen: `ssh pve01 'sudo pct destroy 199'`.

`restore-drill.yml --check` zegt alleen welke back-up hij zou pakken, zonder
iets te doen.

De drill kiest zelf een container uit wat Proxmox nu draait (geen
OCI-containers zoals `ntfy`), of neemt die van `-e guest=<naam>`.

Het bouwpad zelf (`bin/tofu proxmox apply`, `new-guest.yml`, `bootstrap.yml`,
de baseline) bewijs je gewoon door het te gebruiken: elke nieuwe container
loopt het van begin tot eind.

## Inloggen op PBS

Op [backup.neodata.be](https://backup.neodata.be) kies je bij **Realm**
"Pocket ID (id.neodata.be)". Pocket ID laat alleen de groep `admin` door en
vraagt elke keer je passkey. `root@pam` blijft de noodtoegang.

PBS leest geen groepen uit Pocket ID. Wie admin is op PBS, staat daarom bij
naam in `pbs_oidc.admins` (`inventory/host_vars/pbs/main.yml`); wie er niet
op staat, krijgt geen account. Iemand toevoegen:

```bash
$EDITOR inventory/host_vars/pbs/main.yml   # naam onder pbs_oidc.admins
ansible-playbook playbooks/pbs.yml --tags oidc
```

Iemand weghalen doet de rol niet vanzelf (hij voegt alleen toe):
`proxmox-backup-manager user remove <naam>@pocketid` op `pbs`, en dan de naam
uit de lijst.

## Goed om te weten

### Een nieuw client-secret voor PBS

PBS geeft het secret van de realm nooit terug, dus de rol stuurt het alleen
bij het aanmaken. Vervang je de client in Pocket ID, zet het nieuwe secret dan
in de vault (`vault_pbs_oidc_client_secret`) én met de hand in PBS:
`proxmox-backup-manager openid update pocketid --client-key <secret>`.

### De twee back-upjobs

| | Dagelijks | Wekelijks |
| --- | --- | --- |
| Wanneer | elke nacht 02:30 | zondag 01:00 |
| Waarheen | PBS (`pbs`), op pve01 zelf | de Mac mini (`macmini-backup`) |
| Welke guests | alle behalve 100 (PBS) | 101, 102, 103, 104, 106, 107, 108 |
| Hoe | incrementeel, gededupliceerd | volledige `.tar.zst`/`.vma.zst`-dumps |
| Bewaart | 7 | 2 |
| Versleuteld | ja | **nee** |
| Redt je van | een kapotte guest | een pve01 die weg is |

De dagelijkse is de hoofdkopie. Maar die staat op pve01 zelf: sterft die
machine met zijn schijven, dan gaan guests en back-ups samen. Daarvoor is de
wekelijkse. Bron: `inventory/group_vars/proxmox/backup.yml` en `storage.yml`.

### Buiten het huis: Cloudflare R2

De dagelijkse en de wekelijkse kopie staan allebei in huis. Sinds 25-09-2026
gaat er elke nacht om 04:00 ook een kopie naar Cloudflare R2, maar **alleen
wat git niet kan herbouwen** (zie [Terughalen uit R2](/proxmox/r2/#terughalen-uit-r2)). Zo
past het in de gratis 10 GB: op 25-09 was het 3,1 GB.

| Tijd | Wat |
| --- | --- |
| 02:00 | `docker` maakt een back-up van zijn app-data en foto's naar PBS (`docker-data-backup.timer`) |
| 02:30 | de gewone back-up van alle machines naar PBS |
| 04:00 | `r2-guard` telt wat er in R2 staat. Onder de drempel start hij zelf de kopie van de gekozen groepen naar R2 (de laatste 3 versies), en meet daarna opnieuw |

| Keuze | Waarom |
| --- | --- |
| alleen r2-guard start de sync, de job heeft geen schema | Cloudflare kent geen harde uitgavengrens voor R2. r2-guard checkt eerst; bij twijfel of een crash gaat er die nacht niets heen |
| stop boven 8 GB, 800.000 Class A- of 8.000.000 Class B-operaties per maand; waarschuwing vanaf 6,5 GB | wat één nacht uploadt, weet hij pas achteraf. De 2 GB onder de gratis 10 GB vangt een drukke nacht op |
| r2-guard telt de bucket zelf | de cijfers van Cloudflare lopen tot een dag achter (op 25-09: 0 GB bij 3 GB) |
| nooit wissen in R2 (`remove-vanished` uit) | anders wist een lege `store1` (na een herbouw of ransomware) alles in R2, net als je het nodig hebt. Oude versies ruimt de prune job op |

Ansible dwingt dit af: komt er een schema of `remove-vanished` bij, dan haalt
de volgende run het weg.

De dumps op de Mini zijn niet versleuteld: iedereen die die NFS-share kan
mounten, kan ze lezen. Die in R2 wel: Cloudflare ziet alleen versleutelde
blokken.

### Faalt de wekelijkse job, dan meldt niemand dat

Slaapt de Mini op zondagnacht, of is de share weg, dan faalt de job stil. Kijk
af en toe zelf:

```bash filename="laptop"
ssh pve01 'sudo pvesm list macmini-backup'
ssh pve01 'df -h /mnt/pve/macmini-backup'
```

### Waarom maar twee dumps bewaren

`media01` op de Mini is bijna vol en draagt ook Time Machine.
Daarom staat `prune-backups keep-last=2` op de opslag (ongeveer 50 GB). Wil je
meer, kijk dan eerst `df` op de Mini. Loopt die schijf vol, dan breken beide
back-ups tegelijk.
