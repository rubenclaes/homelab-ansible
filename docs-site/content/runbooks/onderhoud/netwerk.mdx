# Netwerk en Proxmox

Iets aan het netwerk of aan de Proxmox-node zelf. Geen van deze dingen zit in
`site.yml`: je draait ze bewust, met de hand.

## Welk geval ben jij?

| Jouw situatie | Voorbeeld | Ga naar |
| --- | --- | --- |
| Je wil een **IP-adres of bridge** van de hypervisor aanpassen | `vmbr1` krijgt een ander adres | [Bridges van pve01 wijzigen](#bridges-van-pve01-wijzigen) |
| Na een herbouw starten guests **niet mee op** als pve01 opstart | na een restore staat de helft op `onboot: 0` | [Guests mee laten opstarten](#guests-mee-laten-opstarten) |
| Een host moet een **andere DNS-server** gebruiken | `caddy` wijst nog naar een oude resolver | [DNS-server van een host omzetten](#dns-server-van-een-host-omzetten) |
| Een toestel staat in AdGuard als **kaal IP of `iPhone`** en je wil een echte naam | de iPhone van Karen, de Nuki | [Een toestel een naam geven](#een-toestel-een-naam-geven) |
| Je wil nakijken of je **van buitenaf** nog binnenkomt | de VPN op je iPhone doet niets meer | [De VPN nakijken](#de-vpn-nakijken) |
| Je wil weten **hoe DNS en de VPN nu in elkaar zitten** | "welke resolver gebruikt `docker`?" | [Hoe het netwerk nu staat](/homelab/netwerk/) |

## Bridges van pve01 wijzigen

Een IP-adres of bridge van de hypervisor aanpassen, bijvoorbeeld `vmbr1`
krijgt een ander adres.

<Callout type="error">
Dit is het gevaarlijkste playbook in de repo. Ansible bereikt `pve01` op
`192.168.0.10`, en dat ís `vmbr0`. Een fout geeft geen rode taak, maar een
onbereikbare hypervisor. **Weet waar de machine fysiek staat** voor je begint.
</Callout>

<Steps>

#### Kijk wat er nu echt staat

```bash
ssh pve01 cat /etc/network/interfaces
```

Vergelijk dit met `inventory/group_vars/proxmox/network.yml`. Die waarden zijn
één keer overgetikt en sindsdien niet opnieuw nagelopen. Verschillen ze al vóór
jouw wijziging? Zet eerst de inventory recht.

#### Pas de inventory aan

```bash
$EDITOR inventory/group_vars/proxmox/network.yml
```

De bridges staan onder `pve_node_interfaces`:

| Veld | Voorbeeld | Doet |
| --- | --- | --- |
| `iface` | `vmbr1` | naam van de bridge |
| `cidr` | `192.168.0.14/24` | adres van de node op die bridge |
| `gateway` | `192.168.0.1` | alleen op `vmbr0`, daar zit de default route |
| `bridge_ports` | `nic0` | de fysieke poort eronder |

#### Kijk droog wat er zou veranderen

```bash
ansible-playbook playbooks/proxmox-network.yml --check --diff
```

`changed=0` betekent: de inventory en de node zijn het eens.

#### Zet de wijziging klaar (nog niet actief)

```bash
ansible-playbook playbooks/proxmox-network.yml                        # schrijft alleen interfaces.new
ssh pve01 diff /etc/network/interfaces /etc/network/interfaces.new    # dit gaat er veranderen
```

Zonder vlag schrijft het playbook alleen `/etc/network/interfaces.new`. Wat
draait blijft ongemoeid.

#### Pas toe

```bash
ansible-playbook playbooks/proxmox-network.yml -e proxmox_network_apply=true
```

Nu herlaadt de node zijn netwerk. Gaat er iets mis, dan zet de
[dodemansknop](#de-dodemansknop)
de oude config na 180 seconden vanzelf terug.

<Callout type="warning">
Weigert het playbook met `ansible-network-revert.timer is still armed`? Dan
loopt er nog een terugzet-timer van een vorige run. De config die nu draait is
misschien net de kapotte. Wacht tot de timer afgaat (max. 3 minuten), of, als
je **zeker** weet dat wat draait goed is:

```bash
ssh pve01 sudo systemctl stop ansible-network-revert.timer
```
</Callout>

#### Controleer de bridges

```bash
ssh pve01 systemctl is-active ansible-network-revert.timer   # moet 'inactive' zijn
ssh pve01 cat /etc/network/interfaces                          # jouw nieuwe waarden?
```

Is de timer afgegaan en staat de oude config terug? Kijk waarom:

```bash
ssh pve01 journalctl -u ansible-network-revert.service
```

#### Commit en push

```bash
git add inventory/group_vars/proxmox/network.yml
git commit -m 'pve01: bridges aangepast'
git push
```

</Steps>

## Guests mee laten opstarten

Na een herbouw of restore starten guests niet mee op als pve01 opstart: ze
staan op `onboot: 0`.

<Steps>

#### Bedenk welke guests níét mogen meestarten

Het playbook zet `onboot` aan op **elke** guest die het uit heeft staan, ook op
een guest die je bewust uit liet.

#### Draai het playbook

```bash
ansible-playbook playbooks/proxmox-autostart.yml
```

De uitvoer toont per aangepaste guest `<vmid> <naam>`.

#### Zet de uitzonderingen terug uit

```bash
ssh pve01 sudo pct set <vmid> --onboot 0    # voor een LXC
ssh pve01 sudo qm set <vmid> --onboot 0     # voor een VM
```

</Steps>

<Callout type="info">
Waarom dit niet in `site.yml` zit: zie
[Goed om te weten](#waarom-proxmox-autostartyml-niet-in-siteyml-zit).
</Callout>

## DNS-server van een host omzetten

Een host moet een andere resolver gebruiken. Voorbeeld: `caddy` (ct 106) moet
`192.168.0.29` gebruiken.

<Steps>

#### Kijk eerst hoe de host zijn DNS regelt

```bash
ssh caddy 'ls -l /etc/resolv.conf'
```

- **Een pijl `->` in de uitvoer?** Dan beheert systemd-resolved het bestand. Ga naar de stap *Via netplan*.
- **Geen pijl?** Dan is het een gewoon bestand. Ga naar de stap *Gewoon bestand*.

<Callout type="warning">
Een `sed` op een gesymlinkte `resolv.conf` lijkt te werken, maar is bij de
volgende netwerkwijziging weer weg. Kijk dus altijd eerst welk van de
mechanismen de host gebruikt.
</Callout>

#### Via netplan (bij een symlink)

```bash
ssh -t docker 'sudoedit /etc/netplan/90-default.yaml'   # zet 192.168.0.29 onder nameservers
ssh docker 'sudo netplan apply'
```

Zo staat het op `docker` en `docker-grafana-stack`.

#### Gewoon bestand (zonder symlink)

```bash
ssh -t caddy 'sudoedit /etc/resolv.conf'   # nameserver 192.168.0.29
```

#### Zet het ook in de LXC-config (alleen bij een LXC)

```bash
ssh pve01 'sudo pct config 106 | grep search'   # welk searchdomain heeft hij nu?
ssh pve01 'sudo pct set 106 --nameserver 192.168.0.29 --searchdomain home.arpa'
```

Anders draait een herstart van de container je wijziging terug. Geef
`--searchdomain` altijd mee (de waarde die je net zag), want die verschilt per
container.

<Callout type="error">
Nooit op `tailscale` (ct 108): daar staat `100.100.100.100` en dat beheert
tailscaled zelf voor MagicDNS.
</Callout>

#### Controleer de resolver

```bash
ssh caddy 'getent hosts pve01.home.arpa'   # 192.168.0.10 - vanaf de host zelf
dig +short pve01.home.arpa                 # 192.168.0.10 - vanaf je werkstation
dig +short books.neodata.be                # 192.168.0.25 - de wildcard naar Caddy
```

`pve01.home.arpa` bewijst het: die naam kent alleen de AdGuard in ct 107.

#### Controleer alle namen in één keer

```bash
ansible-playbook playbooks/smoketest.yml --tags dns
```

Vraagt elke naam uit de inventory op bij AdGuard en vergelijkt het antwoord.
Zie [Onderhoud](/runbooks/onderhoud/) voor wat hij wel en niet dekt.

</Steps>

Welke host welke resolver hoort te hebben: zie
[Hoe het netwerk nu staat](/homelab/netwerk/#wie-gebruikt-welke-dns).

## De VPN nakijken

Je komt van buitenaf niet meer binnen. WireGuard "Neodata VPN" staat in de
**UniFi-controller**, niet in deze repo.

<Steps>

#### Controleer of het adres nog klopt

```bash
dig +short vpn.neodata.be
```

Vergelijk met het WAN-adres in UniFi. Verschillen ze, dan is je provider van
IP gewisseld en heeft de Dynamic DNS in UniFi de record niet (of nog niet)
bijgewerkt. Kijk die regel na, en open hem en klik **Save** om een update te
forceren. Zie
[Het WAN-adres is dynamisch](#het-wan-adres-is-dynamisch).

#### Controleer de DNS die de VPN uitdeelt

| Waar | Veld | Waarde | Waarom |
| --- | --- | --- | --- |
| UniFi → de VPN-server "Neodata VPN" | DNS-server | `192.168.0.29` | de AdGuard in ct 107; alleen die kent de `*.home.arpa`-namen |

<Callout type="warning">
Heb je de DNS-server gewijzigd? **Importeer het profiel opnieuw op de
telefoon.** De waarde zit ingebakken in de clientconfig; alleen de server
aanpassen is niet genoeg.
</Callout>

#### Test via mobiele data

Zet wifi uit op je telefoon, zet de VPN aan en open `pve01.home.arpa`, of ping
het. Werkt die naam, dan werkt de hele keten: VPN, route én DNS.

</Steps>

Hoe de VPN nu staat (endpoint, subnet, profielen): zie
[Twee wegen naar binnen](/homelab/netwerk/#twee-wegen-naar-binnen).

## Een toestel een naam geven

De Query Log van AdGuard toont `192.168.0.23` of `iPhone`, en je wil
`iphone-karen`. De naam komt uit UniFi, niet uit AdGuard: AdGuard vraagt bij
elk IP aan de UCG wie dat is.

<Steps>

#### Geef het toestel een vast adres en een DNS-record in UniFi

| Waar | Veld | Waarde | Waarom |
| --- | --- | --- | --- |
| UniFi → Client Devices → het toestel → Settings | Fixed IP Address | aan, het huidige adres | zonder vast adres maakt UniFi geen record |
| idem, net eronder | Local DNS Record | aan, `<naam>.home.arpa` | alleen `<naam>` weigert UniFi met "must be a valid hostname" |

Kleine letters, cijfers en `-`, geen spaties.

#### Zet het in git

In `inventory/group_vars/all/unifi.yml`, onder `unifi_dns_names`:

```yaml
  "46:bf:32:25:e6:9c": iphone-karen
```

Zonder `.home.arpa`. De MAC staat in UniFi bij het toestel. Is het een nieuw
toestel, zet de MAC dan ook in `unifi_known_macs`, anders blijft
`unifi-watch.yml` erover melden.

#### Controleer

```bash
dig +short -x 192.168.0.23 @192.168.0.29
ansible-playbook playbooks/unifi-routes.yml
```

De eerste geeft `iphone-karen.home.arpa.`. De tweede is groen; hij draait ook
elke ochtend in Semaphore en wordt rood als het record in UniFi verdwijnt of
anders heet.

#### Commit en push

</Steps>

<Callout type="info">
Op een iPhone: **Settings → Wi-Fi → (i) bij je netwerk → Private Wi-Fi
Address → Fixed**. Op **Rotating** krijgt de telefoon af en toe een nieuwe
MAC. UniFi ziet dan een nieuw toestel, en het vaste adres en de naam horen bij
het oude.
</Callout>

## Goed om te weten

### Waarom de bridges niet in `site.yml` zitten

`proxmox_network_apply` staat op `false` in de rol-defaults en mag nergens in de
inventory op `true`. Een gewone run die de bridges van de hypervisor kan
herschrijven, kan in één keer alles platleggen. Toepassen doe je alleen per
run, met de vlag op de commandline.

### De dodemansknop

Met de vlag gebeurt dit:

1. de draaiende config wordt gekopieerd naar `/etc/network/interfaces.before-ansible`
2. een `systemd-run`-timer wordt gewapend die die kopie na **180 seconden** terugzet en `ifreload -a` draait
3. de nieuwe config wordt via de Proxmox-API toegepast
4. vanaf je werkstation wordt elk adres uit `pve_node_interfaces` op poort 22 geprobeerd
5. lukt dat, dan wordt de timer gestopt

Valt het playbook ergens tussenuit, dan komt de node vanzelf terug op een
config die werkte. De test draait bewust vanaf je werkstation: op de node zelf
slaagt hij altijd, dus bewijst hij niets.

### Waarom 180 seconden

Kopiëren en wapenen duren elk een seconde, toepassen ongeveer vijftien, en de
test in het slechtste geval twee keer twintig. Samen zo'n tachtig, plus marge.
Te lang is veiliger dan te kort: te vroeg terugzetten kost je een nieuwe poging,
te laat laat je wachten met een onbereikbare hypervisor.

### Waarom `proxmox-autostart.yml` niet in `site.yml` zit

Een guest die bewust níét meestart, zou bij elke run stilletjes weer aangezet
worden. Meestal draai je dit één keer, na een herbouw.

### Waarom de naam in UniFi staat en niet in AdGuard

AdGuard kan zelf ook namen geven (Settings → Client settings). Dan zou elk
toestel op twee plaatsen staan, en krijgt een toestel een ander IP, dan klopt
AdGuard niet meer. Nu is UniFi de enige bron: hij deelt het adres uit en kent
dus altijd de juiste naam. AdGuard vraagt het hem via `local_ptr_upstreams`.

De **alias** in UniFi telt daarvoor niet. De UCG geeft AdGuard alleen het
Local DNS Record, of anders de naam die het toestel zelf opgeeft (`iPhone`,
`Mac`, `LGwebOSTV`).

Ansible schrijft niet naar UniFi, net als bij de DNS die de netwerken
uitdelen: `unifi-routes.yml` vergelijkt alleen. De eerste lading records is op
25-09 wel via de API gezet, eenmalig.

### Waarom DNS naar ct 107 moest

De DNS van het huis hing eerst aan de AdGuard op de Mac mini, die in geen enkel
playbook stond. Dat is dezelfde machine die de NFS-shares exporteert: viel hij
om, dan verloor je naamresolutie én media-opslag tegelijk. ct 107 beschrijft
Ansible en neemt PBS mee in de back-up.

### Waarom de tailnet een 100.x-adres als DNS heeft

Een LAN-adres (`192.168.0.29`) als tailnet-nameserver werkt alleen voor
toestellen die de subnet-route accepteren. Onderweg heb je dan helemaal geen
DNS. Daarom zit ct 107 zelf op de tailnet, met `--accept-dns=false` zodat hij
zijn DNS niet via een omweg bij zichzelf gaat halen.

### Het WAN-adres is dynamisch

Je provider kan je WAN-adres veranderen. Daarom werkt UniFi `vpn.neodata.be`
zelf bij in Cloudflare:

| Waar | Wat |
| --- | --- |
| UniFi → Settings → Internet → WAN → Advanced → Dynamic DNS | service **Cloudflare**, hostname `vpn.neodata.be` |

Dat staat in UniFi, niet in deze repo. Het WireGuard-profiel op je toestel
gebruikt de naam `vpn.neodata.be`, niet het adres, dus na een wissel volgt het
vanzelf. UniFi kan bij de VPN-server nog waarschuwen dat hij op "Existing IP
Address" staat; met Dynamic DNS actief mag die waarschuwing blijven staan.

Sinds 4 september is het adres niet gewisseld, dus de update is nooit echt
nodig geweest. Werkt WireGuard na een wissel niet, kijk dan of de record
gevolgd is: zie [De VPN nakijken](#de-vpn-nakijken).
