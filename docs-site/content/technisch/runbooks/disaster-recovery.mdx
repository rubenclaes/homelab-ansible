# Herstellen

Er is iets stuk en je wil het terug. Kies in de tabel wat er stuk is en volg
dan alleen dat geval, stap voor stap.

<Callout type="info">
Deze pagina draait op `docs.neodata.be`, en dat is de container `caddy`. Is
die weg, dan is deze pagina ook weg. Dezelfde tekst staat in elke clone van
de repo: `docs-site/content/technisch/runbooks/disaster-recovery.mdx`.
</Callout>

## Welk geval ben jij?

| Jouw situatie | Voorbeeld | Ga naar |
| --- | --- | --- |
| Een container is stuk, en er staat niets op dat je niet opnieuw kan maken | `caddy`, `tailscale` | [Geval 1 — Container opnieuw bouwen](#geval-1--container-opnieuw-bouwen) |
| Een container of VM is stuk, en **wat erop stond** moet terug | `adguard`, `semaphore`, `docker`, Home Assistant | [Geval 2 — Terugzetten uit de back-up](#geval-2--terugzetten-uit-de-back-up) |
| Niets resolvet meer: geen `*.home.arpa`, geen `*.neodata.be` | `adguard` (ct 107) ligt plat | [Geval 3 — Geen DNS](#geval-3--geen-dns) |
| De media-apps draaien, maar hun mappen zijn leeg | Sonarr of Radarr ziet geen bestanden | [Geval 4 — De shares van de Mac mini](#geval-4--de-shares-van-de-mac-mini) |
| De Mac mini is kapot of opnieuw geïnstalleerd | nieuwe schijf, macOS opnieuw | [Geval 5 — De Mac mini is weg](#geval-5--de-mac-mini-is-weg) |
| `pve01` zelf is weg | Proxmox opnieuw geïnstalleerd | [Geval 6 — pve01 is weg](#geval-6--pve01-is-weg) |
| De back-ups op PBS zijn weg of onleesbaar | schijf `vm-hdd` kapot, of de sleutel kwijt | [Geval 7 — Terugvallen op de tweede kopie](#geval-7--terugvallen-op-de-tweede-kopie) |

Twijfel je tussen 1 en 2: kies **2**. Een back-up terugzetten kan altijd.

**Is er nu niets stuk?** Doe dan eerst [Vooraf: doe dit nu](#vooraf-doe-dit-nu).
Zonder die stappen werkt geen enkel geval hieronder.

### Woorden die je nodig hebt

**Node** — de fysieke machine `pve01` (`192.168.0.14`), met Proxmox erop.

**Guest** — een container (LXC, commando's `pct`) of virtuele machine (VM,
commando's `qm`) op die node. Elke guest heeft een nummer, de *vmid*.

**PBS** — Proxmox Backup Server, VM 100. Hij bewaart de dagelijkse back-ups,
versleuteld, op de schijf `vm-hdd` van pve01 zelf.

**Tweede kopie** — de wekelijkse back-up naar de Mac mini (`macmini-backup`).
Niet versleuteld.

### Welke guest is wat

| Guest | vmid | Soort | Opslag | Bij verlies |
| --- | --- | --- | --- | --- |
| `pbs` | 100 | VM | `local-lvm` + `vm-hdd` | met de hand, zie [geval 6](#geval-6--pve01-is-weg) |
| `haos` (Home Assistant) | 101 | VM | `vm-hdd` | back-up (geval 2) |
| `docker-grafana-stack` | 102 | VM | `vm-hdd` | back-up (geval 2) |
| `docker` | 103 | VM | `vm-hdd` | back-up (geval 2) |
| `semaphore` | 104 | LXC | `local-lvm` | back-up (geval 2) |
| `caddy` | 106 | LXC | `vm-hdd` | opnieuw bouwen (geval 1) |
| `adguard` | 107 | LXC | `vm-hdd` | back-up (geval 2 of 3) |
| `tailscale` | 108 | LXC | `vm-hdd` | opnieuw bouwen (geval 1) |

Bron: `inventory/group_vars/proxmox/lxcs.yml` en `vms.yml`.

## Vooraf: doe dit nu

Doe dit terwijl alles nog werkt. Achteraf kan het niet meer.

<Steps>

### Maak een papieren kopie van de PBS-sleutel

```bash
ssh pve01
sudo ls /etc/pve/priv/storage/                                         # hier hoort pbs.enc te staan
sudo proxmox-backup-client key paperkey /etc/pve/priv/storage/pbs.enc --output-format text
```

Print wat eruit komt, en bewaar het **buiten het huis**. Zonder deze sleutel
zijn de back-ups op PBS niet terug te zetten.

<Callout type="warning">
`proxmox-backup-client key show` toont alleen de vingerafdruk van de sleutel,
niet de sleutel zelf. Daar kan je niets mee terugzetten.
</Callout>

### Bewaar de twee vault-wachtwoorden op dezelfde plek

```bash
cat ~/.ansible/vault_pass_infra
cat ~/.ansible/vault_pass_stacks
```

Ze openen alles wat de repo versleuteld bewaart: API-tokens, logins, de
`.env`-bestanden van de stacks. Ze staan niet in git, met opzet.

<Callout type="error">
Kwijt = de repo is compleet maar onbruikbaar. Bijna elk playbook leest een
vault-bestand. Ze zijn nergens uit af te leiden: de enige weg terug is elk
vault-bestand opnieuw maken en elk secret opnieuw zetten.
</Callout>

</Steps>

## Geval 1 — Container opnieuw bouwen

Voor een container waar niets unieks op staat: `caddy` en `tailscale`. Een
nieuwe bouwen gaat sneller dan een back-up terugzetten, en is schoner.

Voorbeeld: `caddy` (ct 106).

<Steps>

### Gooi de oude weg (als hij nog half bestaat)

```bash
ssh pve01 'sudo pct stop 106; sudo pct destroy 106'
```

Het playbook maakt alleen wat ontbreekt. Een halve container blijft anders
gewoon staan.

### Bouw hem opnieuw

```bash
ansible-playbook playbooks/new-guest.yml -e guest=caddy
```

Maakt de container, zet het `ansible`-account erop en doet de baseline.

### Alleen bij `tailscale`: geef hem `/dev/net/tun`

Zet als root op pve01 deze twee regels onderaan `/etc/pve/lxc/108.conf`:

```bash
ssh -t pve01 'sudoedit /etc/pve/lxc/108.conf'
```

```
lxc.cgroup2.devices.allow: c 10:200 rwm
lxc.mount.entry: /dev/net/tun dev/net/tun none bind,create=file
```

```bash
ssh pve01 'sudo pct reboot 108'
```

Zonder dit start `tailscaled` niet. Het API-token mag deze regels niet zetten,
dus geen playbook kan het voor je doen.

### Zet de dienst terug

```bash
ansible-playbook playbooks/site.yml --limit caddy
```

### Alleen bij `caddy`: zet de docs en het rapport terug

```bash
ansible-playbook playbooks/caddy-smoketest.yml
ansible-playbook playbooks/docs.yml       # docs.neodata.be staat op caddy
ansible-playbook playbooks/report.yml     # report.neodata.be ook
```

Een nieuwe `caddy` is leeg: de routes werken, maar deze site en het rapport
staan er pas weer na deze twee.

### Laat Semaphore de nieuwe machine vertrouwen

```bash
ansible-playbook playbooks/semaphore.yml
```

De nieuwe container heeft een nieuwe SSH-hostkey. Semaphore weigert hem tot
deze run. Niet met `--limit semaphore`: dan faalt hij.

</Steps>

## Geval 2 — Terugzetten uit de back-up

Voor alles waarvan de schijf het punt is: `adguard` (filterinstellingen,
upstreams), `semaphore` (projecten, geschiedenis), `docker`, Home Assistant.

Voorbeeld: `adguard` (ct 107). Alle commando's met `pct`/`qm`/`pvesm` draai je
op pve01 (`ssh pve01`).

<Steps>

### Zoek de back-up die je wil

```bash
sudo pvesm list pbs | grep '/107/'
```

Je krijgt volledige namen zoals `pbs:backup/ct/107/2026-09-20T02:30:00Z`.
Kopieer de **nieuwste van vóór de storing**, in zijn geheel.

### Twijfel je? Test hem eerst ernaast

```bash
sudo pct restore 199 pbs:backup/ct/107/2026-09-20T02:30:00Z --storage vm-hdd
sudo pct set 199 --delete net0     # netwerkkaart eraf: anders botst hij met het origineel
sudo pct start 199
sudo pct exec 199 -- ls /opt/AdGuardHome   # kijk of je data erin staat
sudo pct stop 199; sudo pct destroy 199
```

Dit raakt het origineel niet aan. Of laat een playbook het doen:
`ansible-playbook playbooks/restore-drill.yml -e drill_confirm=true -e guest=adguard`.

<Callout type="warning">
Vergeet `--delete net0` niet. De back-up draagt het IP en MAC-adres van het
origineel: start je hem zo, dan heb je twee machines op hetzelfde adres.
</Callout>

### Zet het origineel stil

```bash
sudo pct stop 107     # een VM: sudo qm stop 103
```

### Zet de back-up terug

**Een container:**

```bash
sudo pct restore 107 pbs:backup/ct/107/2026-09-20T02:30:00Z --storage vm-hdd --force
```

**Een VM:**

```bash
sudo qmrestore pbs:backup/vm/103/2026-09-20T02:30:00Z 103 --storage vm-hdd --force
```

`--force` overschrijft wat er op dat nummer staat. Kijk dus twee keer naar
het nummer. Bestaat de guest niet meer, dan mag `--force` weg.

<Callout type="warning">
De volgorde verschilt: bij `pct restore` komt **het nummer eerst**, bij
`qmrestore` **de back-up eerst**. Dat is geen typefout.

`--storage`: neem dezelfde als het origineel (zie [de tabel](#welke-guest-is-wat)).
`semaphore` staat op `local-lvm`, de rest op `vm-hdd`.
</Callout>

### Start hem

```bash
sudo pct start 107    # een VM: sudo qm start 103
```

### Trek hem gelijk met de repo

Terug op je werkstation:

```bash
ansible-playbook playbooks/site.yml --limit adguard
```

De back-up draait de configuratie van toen. Deze run brengt hem naar wat de
repo nu zegt.

<Callout type="info">
Terugzetten van `semaphore`? Gebruik dan `ansible-playbook playbooks/semaphore.yml`
in plaats van `site.yml --limit semaphore`. Die laatste faalt: Semaphore moet
eerst de hostkeys van alle machines ophalen.
</Callout>

### Krijg je "REMOTE HOST IDENTIFICATION HAS CHANGED"?

```bash
ssh-keygen -R 192.168.0.29    # het adres van de teruggezette guest
```

</Steps>

## Geval 3 — Geen DNS

Niets resolvet: `*.home.arpa` niet en `*.neodata.be` niet. Alle DNS van het
huis loopt via één container: `adguard`, ct 107, `192.168.0.29`.

**Ansible werkt nog.** De inventory gebruikt IP-adressen, geen namen.

<Steps>

### Kijk of hij gewoon uit staat

```bash
ssh pve01 'sudo pct status 107'
ssh pve01 'sudo pct start 107'     # als hij "stopped" zegt
```

### Is hij stuk: zet hem terug uit de back-up

Volg [geval 2](#geval-2--terugzetten-uit-de-back-up) met vmid 107. Dat is de
snelle en volledige weg.

<Callout type="warning">
Liever **niet** opnieuw bouwen. Een nieuwe AdGuard mist alles wat alleen in de
container staat: je login, de upstream-resolvers, en de wildcard
`*.neodata.be → 192.168.0.25`, die met de hand in AdGuard staat. Bovendien
vraagt een nieuwe container zijn DNS aan pve01, en die vraagt het aan…
de AdGuard die er niet is. Dan faalt de installatie.
</Callout>

### Geen back-up? Dan toch opnieuw bouwen

```bash
ansible-playbook playbooks/new-guest.yml -e guest=adguard
```

Loopt dit vast op het downloaden van pakketten, geef de container dan zijn
eigen DNS en draai het opnieuw:

```bash
ssh pve01 'sudo pct set 107 --nameserver 1.1.1.1; sudo pct reboot 107'
ansible-playbook playbooks/new-guest.yml -e guest=adguard
```

Daarna, met de hand:

1. zet de `/dev/net/tun`-regels in `/etc/pve/lxc/107.conf`, zoals bij `tailscale` in [geval 1](#geval-1--container-opnieuw-bouwen), en `pct reboot 107`
2. loop de setup-wizard af op `http://192.168.0.29:3000`, met dezelfde login als in `inventory/host_vars/adguard/vault.yml`
3. zet in AdGuard de upstream-DNS en de rewrite `*.neodata.be` → `192.168.0.25`

```bash
ansible-playbook playbooks/site.yml --limit adguard   # rewrites *.home.arpa + filterlijsten
```

### Test

```bash
ansible-playbook playbooks/dns-smoketest.yml
```

Vraagt elke naam uit de inventory op bij AdGuard, plus één publieke naam
(`google.com`) om te zien of doorvragen werkt.

### Kwam hij terug op een ander adres?

Pas dan de DNS-server aan in UniFi (DHCP). Anders blijft het huis zoeken naar
`192.168.0.29`.

</Steps>

<Callout type="info">
Zet in UniFi altijd `1.1.1.1` als tweede DNS-server naast `192.168.0.29`.
Zonder tweede heeft het hele huis geen internet als ct 107 stilstaat, ook het
toestel waarmee je het wil repareren niet.
</Callout>

## Geval 4 — De shares van de Mac mini

De media-apps op `docker` draaien, de routes werken, maar de mappen zijn
leeg. Dan mist `docker` de NFS-shares van de Mac mini. Dat is de stilste
storing in dit huis.

<Steps>

### Zet de shares terug op de Mac mini

```bash
ansible-playbook playbooks/nfs.yml -K
```

`-K` vraagt je sudo-wachtwoord van de Mini. Dat hoort zo.

Fout `[Errno 1] Operation not permitted` op `/etc/exports`? Zie
[TCC: sshd moet Volledige schijftoegang hebben](#tcc-sshd-moet-volledige-schijftoegang-hebben).

### Mount ze opnieuw op `docker`

```bash
ansible-playbook playbooks/stacks.yml --limit docker
```

Mount de drie shares (`/mnt/media01`, `/mnt/faststore`, `/mnt/ssdnas`) en
zet de stacks op.

### Herstart de media-stack

```bash
ssh docker 'sudo docker restart $(sudo docker ps -q --filter label=com.docker.compose.project=media-stack)'
```

Een container die startte toen de share er niet was, blijft in de lege map
kijken tot hij herstart.

</Steps>

| Export op de Mini | Mount op `docker` |
| --- | --- |
| `/Volumes/media01` | `/mnt/media01` |
| `/Volumes/FastStore` | `/mnt/faststore` |
| `/Volumes/SSD Nas` | `/mnt/ssdnas` |

Bron: `nfs_exports_shares` in `inventory/host_vars/macmini.yml` en
`docker_stacks_nfs_mounts` in `inventory/host_vars/docker.yml`.

## Geval 5 — De Mac mini is weg

Wat je kwijt bent:

| Weg | Gevolg |
| --- | --- |
| de tweede back-upkopie (`macmini-backup`) | alleen PBS nog, en die staat op pve01 zelf |
| de drie NFS-shares | de media-stack op `docker` valt om |
| Plex en zes compose-stacks | die draaien nergens anders |

pve01, PBS en de guests zijn ongemoeid.

<Callout type="error">
Dit pad is **nooit volledig gelopen**. `nfs.yml` heeft één keer echt gedraaid,
`stacks.yml --limit macmini` alleen droog. Reken op verrassingen, vooral rond
Homebrew: de Mini draait macOS 14, waar alles vanaf broncode bouwt.
</Callout>

<Steps>

### Installeer macOS en geef hem hetzelfde adres

Hij moet weer op `192.168.0.26`. Dat adres staat vast in de inventory, in de
mounts van `docker` en in de opslag `macmini-backup` op pve01.

Geef de schijven **dezelfde namen**: `media01`, `FastStore`, `SSD Nas`.

### Geef Ansible toegang

Zet op de Mini *Extern inloggen* (SSH) aan. Dan, vanaf je werkstation:

```bash
ssh-copy-id -i ~/.ssh/ansible_ed25519.pub rubenclaes@192.168.0.26
```

Ansible logt op de Mini in als `rubenclaes`, niet als `ansible`.

### Geef `sshd` Volledige schijftoegang

Op de Mini zelf:

> Systeeminstellingen → Privacy en beveiliging → Volledige schijftoegang → `+`
> → cmd-shift-G → `/usr/libexec/sshd-keygen-wrapper`

Zonder dit faalt de volgende stap. Uitleg: [TCC](#tcc-sshd-moet-volledige-schijftoegang-hebben).

### Zet de shares terug

```bash
ansible-playbook playbooks/nfs.yml -K
```

Eerst dit: `docker` wacht erop. Volg daarna stap 2 en 3 van
[geval 4](#geval-4--de-shares-van-de-mac-mini).

### Installeer Plex en OrbStack met de hand

Allebei staan ze buiten Homebrew en geen playbook zet ze terug. Zonder
OrbStack is er geen Docker op de Mini. Het waarom staat in
`inventory/host_vars/macmini.yml`.

### Zet brew en casks terug

```bash
ansible-playbook playbooks/site.yml --limit macmini
```

### Maak het Docker-netwerk aan

```bash
ssh rubenclaes@192.168.0.26 '/Applications/OrbStack.app/Contents/MacOS/xbin/docker network create External'
```

De compose-files delen dit netwerk, en geen rol maakt het aan.

### Zet de stacks terug

```bash
ansible-playbook playbooks/stacks.yml --limit macmini
```

De eerste run **faalt op de git clone**, en dat hoort zo. Hij drukt een
publieke sleutel af: zet die op GitHub bij `rubenclaes/homelab` → Settings →
Deploy keys. Draai het daarna opnieuw.

### Maak de back-upmap aan

```bash
ssh rubenclaes@192.168.0.26 "mkdir -p '/Volumes/media01/backups/proxmox'"
ssh pve01 'sudo pvesm status | grep macmini-backup'    # moet "active" zeggen
```

Pas dan komt de tweede kopie terug. De oude dumps zijn weg met de schijf.
Wacht tot zondag 01:00, of start de job met de hand in het Proxmox-scherm:
Datacenter → Backup → de job naar `macmini-backup` → *Run now*.

</Steps>

## Geval 6 — pve01 is weg

Proxmox opnieuw installeren. Dit is de lange weg, en **de volgorde telt**:
elke stap heeft iets nodig van de vorige. Meer uitleg per stap:
[Van niets naar alles, geval 3](/technisch/runbooks/opzetten/#geval-3--pve01-opnieuw-opbouwen).

<Steps>

### Installeer Proxmox op hetzelfde adres

Met de hand, van een USB-stick. Het adres moet `192.168.0.14` zijn: dat staat
vast in `inventory/00-static.yml` en in `pve_api_host`.

### Kijk of de schijf `vm-hdd` het overleefd heeft

Op pve01, als root:

```bash
zpool import vm-hdd
```

- **Lukt het**: de VM-schijven en de PBS-back-ups zijn er nog. Ga door.
- **Lukt het niet**: de PBS-back-ups zijn weg. Doe de stappen hieronder tot en
  met *Zet de overige opslag terug*, en ga dan naar
  [geval 7](#geval-7--terugvallen-op-de-tweede-kopie).

### Maak het API-token

Op pve01, als root. Geen playbook kan dit: een playbook heeft het token zelf
nodig.

```bash
pveum role add AnsibleAutomation --privs "Datastore.AllocateSpace,Datastore.AllocateTemplate,Datastore.Audit,SDN.Use,Sys.Audit,VM.Allocate,VM.Audit,VM.Config.CPU,VM.Config.Disk,VM.Config.Memory,VM.Config.Network,VM.Config.Options,VM.PowerMgmt,VM.GuestAgent.Audit"
pveum user add ansible@pve
pveum acl modify / --user ansible@pve --role AnsibleAutomation
pveum user token add ansible@pve automation --privsep 0   # toont het secret, maar één keer
```

Zet het secret meteen in de vault, op je werkstation:

```bash
ansible-vault edit inventory/group_vars/proxmox/vault.yml   # vault_pve_api_token_secret
```

### Geef Ansible toegang tot pve01

```bash
ssh-keygen -R 192.168.0.14                                   # oude hostkey weg
ansible-playbook playbooks/bootstrap.yml --limit pve01 -u root -k
ansible-playbook playbooks/proxmox-access.yml
ansible-playbook playbooks/site.yml --limit pve01
```

`-u root -k` werkt alleen nu: na de baseline mag root niet meer met een
wachtwoord binnen.

### Maak PBS (VM 100) met de hand

In het Proxmox-scherm, exact volgens `pve_vms` in
`inventory/group_vars/proxmox/vms.yml`. Neem het **MAC-adres** over.

<Callout type="error">
`scsi1` ís de datastore met al je back-ups. Maak die schijf **niet** nieuw aan:
koppel de bestaande uit `vm-hdd`. Een nieuwe schijf is een lege schijf. Dit
stuk is nog nooit gelopen; ga langzaam.
</Callout>

### Koppel de PBS-opslag

Met de hand: Datacenter → Storage → Add → Proxmox Backup Server. Noem hem
`pbs`. Je hebt nodig:

- de encryptiesleutel (je papieren kopie, zie [Vooraf](#vooraf-doe-dit-nu))
- het wachtwoord van `pve@pbs` (niet in de repo; kwijt? zet een nieuw in het PBS-scherm)

Deze stap zit met opzet in geen playbook: de opslag draagt de sleutel, en die
hoort niet in git.

### Zet de overige opslag en de back-upjobs terug

Eerst op de Mac mini (anders blijft `macmini-backup` inactief):

```bash
ssh rubenclaes@192.168.0.26 "mkdir -p '/Volumes/media01/backups/proxmox'"
```

Dan:

```bash
ansible-playbook playbooks/proxmox-datacenter.yml -e proxmox_datacenter_create=true
```

Alleen hier de vlag `-e proxmox_datacenter_create=true`. Zie
[waarom](#waarom-proxmox_datacenter_create-niet-standaard-aan-staat).

### Zet de guests met data terug uit PBS

Volg [geval 2](#geval-2--terugzetten-uit-de-back-up) voor `adguard` (107, als
eerste: DNS), `semaphore` (104), `haos` (101), `docker-grafana-stack` (102) en
`docker` (103). Bestaan ze nog niet, laat `--force` dan weg.

`qmrestore` maakt de VM zelf aan, met de instellingen en het MAC-adres uit de
back-up. Je hoeft 101 tot 103 niet eerst met de hand te maken.

<Callout type="warning">
Kijk na de restore van `adguard` of onderaan `/etc/pve/lxc/107.conf` de twee
`/dev/net/tun`-regels nog staan (zie [geval 1](#alleen-bij-tailscale-geef-hem-devnettun)).
Ontbreken ze, zet ze erbij en doe `pct reboot 107`.
</Callout>

### Haal het container-template op

Op pve01, als root:

```bash
pveam update
pveam download local debian-13-standard_13.1-2_amd64.tar.zst
```

Een verse Proxmox heeft het niet, en de rol haalt het niet zelf op. Het staat
in `pve_lxc_defaults.template` (`lxcs.yml`).

### Bouw de rest opnieuw

```bash
ansible-playbook playbooks/new-guest.yml -e guest=caddy
ansible-playbook playbooks/new-guest.yml -e guest=tailscale
```

Vergeet de `/dev/net/tun`-regels voor `tailscale` niet (zie
[geval 1](#alleen-bij-tailscale-geef-hem-devnettun)).

### Zet de diensten op de nieuwe containers

```bash
ansible-playbook playbooks/caddy.yml
ansible-playbook playbooks/tailscale.yml
ansible-playbook playbooks/semaphore.yml   # niet site.yml --limit semaphore: die faalt
```

Een opnieuw aangemelde `tailscale` biedt `192.168.0.0/24` opnieuw aan. Keur die
route goed in de Tailscale admin console, anders werkt toegang van buitenaf niet.

### Trek alles gelijk

```bash
ansible-playbook playbooks/site.yml --check --diff    # lees dit echt: back-up vs repo
ansible-playbook playbooks/site.yml
ansible-playbook playbooks/docs.yml
ansible-playbook playbooks/report.yml
```

<Callout type="info">
Stopt `stacks.yml` met een deploy-key? Dat gebeurt alleen op een host die
**nieuw** gebouwd is. Zet de getoonde publieke sleutel in GitHub onder
Settings → Deploy keys (`docker` → `rubenclaes/containers`,
`docker-grafana-stack` → `rubenclaes/monitoring-stack`) en draai opnieuw. Kwam
de host uit PBS, dan staat de oude sleutel er nog.
</Callout>

</Steps>

## Geval 7 — Terugvallen op de tweede kopie

Gebruik dit als de PBS-back-ups niet bruikbaar zijn: `vm-hdd` is weg, of je
hebt de encryptiesleutel niet meer. De tweede kopie op de Mac mini is
hoogstens een week oud en heeft **geen sleutel nodig**.

<Steps>

### Zorg dat pve01 de opslag ziet

```bash
ssh pve01 'sudo pvesm status | grep macmini-backup'
```

Staat hij er niet (herbouwde node)? Doe dan eerst de stap
*Zet de overige opslag en de back-upjobs terug* uit [geval 6](#geval-6--pve01-is-weg).

### Zoek de dump

```bash
ssh pve01 'sudo pvesm list macmini-backup'
```

Namen zoals `macmini-backup:backup/vzdump-lxc-107-2026_09_21-01_00_05.tar.zst`
(container) of `…vzdump-qemu-103-….vma.zst` (VM). Neem de nieuwste.

### Zet hem terug

Precies zoals in [geval 2](#geval-2--terugzetten-uit-de-back-up), alleen met
deze naam:

```bash
sudo pct restore 107 macmini-backup:backup/vzdump-lxc-107-2026_09_21-01_00_05.tar.zst --storage vm-hdd
```

### Maak PBS opnieuw, leeg

PBS (VM 100) zit niet in de tweede kopie, met opzet. Maak hem met de hand

## Af en toe: bewijs dat herstellen werkt

Een herstelpad dat nooit gedraaid heeft, is een aanname.

```bash
ansible-playbook playbooks/recovery-drill.yml -e drill_confirm=true
ansible-playbook playbooks/restore-drill.yml -e drill_confirm=true
```

| Playbook | Bewijst | Wanneer |
| --- | --- | --- |
| `recovery-drill.yml` | je kan een container **bouwen** (maken, bootstrap, baseline) | na elke wijziging aan `proxmox_lxc`, `bootstrap.yml`, de baseline of `new-guest.yml` |
| `restore-drill.yml` | je krijgt je **data** terug uit PBS (sleutel werkt, archief heel) | na wijzigingen aan de back-upjobs, en af en toe |

Beide gebruiken vmid 199 en slopen die op het eind. **Faalt een drill, dan
blijft 199 staan**, zodat je kan kijken wat er misging. Opruimen:
`ssh pve01 'sudo pct destroy 199'`.

`restore-drill.yml --check` zegt alleen welke back-up hij zou pakken, zonder
iets te doen.

## Goed om te weten

### De twee back-upjobs

| | Dagelijks | Wekelijks |
| --- | --- | --- |
| Wanneer | elke nacht 02:30 | zondag 01:00 |
| Waarheen | PBS (`pbs`), op pve01 zelf | de Mac mini (`macmini-backup`) |
| Welke guests | alle behalve 100 (PBS) | 101, 102, 103, 104, 106, 107, 108 |
| Hoe | incrementeel, gededupliceerd | volledige `.tar.zst`/`.vma.zst`-dumps |
| Bewaart | 7 | 2 |
| Versleuteld | ja | **nee** |
| Redt je van | een kapotte guest | een pve01 die weg is |

De dagelijkse is de hoofdkopie. Maar die staat op pve01 zelf: sterft die
machine met zijn schijven, dan gaan guests en back-ups samen. Daarvoor is de
wekelijkse. Bron: `inventory/group_vars/proxmox/backup.yml` en `storage.yml`.

### Het is geen off-site

Beide kopieën staan in hetzelfde huis, aan dezelfde stroom, op hetzelfde
netwerk. Tegen brand, diefstal of ransomware helpt dit niet. En de dumps op de
Mini zijn niet versleuteld: iedereen die die NFS-share kan mounten, kan ze
lezen.

### Faalt de wekelijkse job, dan meldt niemand dat

Slaapt de Mini op zondagnacht, of is de share weg, dan faalt de job stil. Kijk
af en toe zelf:

```bash
ssh pve01 'sudo pvesm list macmini-backup'
ssh pve01 'df -h /mnt/pve/macmini-backup'
```

### Waarom maar twee dumps bewaren

`media01` op de Mini is bijna vol en draagt ook Time Machine en Duplicati.
Daarom staat `prune-backups keep-last=2` op de opslag (ongeveer 50 GB). Wil je
meer, kijk dan eerst `df` op de Mini. Loopt die schijf vol, dan breken alle
drie de back-ups tegelijk.

### Waarom `proxmox_datacenter_create` niet standaard aan staat

Op een gezonde node betekent ontbrekende opslag: "de inventory klopt niet". Op
een herbouwde node: "de inventory is de waarheid, maak het aan". Alleen jij
weet welke van de twee het is. Daarom zet je de vlag zelf, en alleen bij een
herbouw.

### Waarom VM's niet uit een playbook komen

`vms.yml` beschrijft de vier VM's, maar niets leest dat bestand. Een VM
opnieuw maken geeft een lege schijf, en de waarde zit in de schijf. Voor
101–103 doet `qmrestore` het beter: die zet de schijf én de instellingen
terug. `vms.yml` is er voor PBS (100) en voor als er geen back-up is. Neem dan
zeker het MAC-adres over: daar hangt de DHCP-reservering aan, en `haos`
herkent zichzelf eraan.

### Waarom `nfs.yml` niet in `site.yml` zit

`/etc/exports` schrijven vraagt root, en `sudo` op de Mini vraagt een
wachtwoord. De Linux-hosts hebben een NOPASSWD-regel van `bootstrap.yml`, de
Mini niet. Een geplande run zou dus blijven hangen op dat wachtwoord.

### TCC: sshd moet Volledige schijftoegang hebben

Krijg je `[Errno 1] Operation not permitted` bij het vervangen van
`/etc/exports`, dan is dat **geen** sudo-probleem. `/etc/exports` draagt het
macOS-label `com.apple.macl`, en een proces dat onder `sshd` start mag zo'n
bestand niet aanraken, ook niet als root. Hetzelfde commando werkt lokaal in
Terminal. De oplossing is `sshd` Volledige schijftoegang geven (zie
[geval 5](#geval-5--de-mac-mini-is-weg)) en daarna **opnieuw verbinden**.

Al geprobeerd op 23-09, werkt niet: `unsafe_writes: true`, `xattr -d
com.apple.macl` en in het bestand schrijven in plaats van het vervangen.
Details in `roles/nfs_exports/tasks/main.yml`.

### macOS kan `/etc/exports` niet vooraf nakijken

`nfsd checkexports` leest alleen het echte bestand. De rol schrijft dus eerst
en controleert daarna, en faalt luid als het mis is. Repareer in
`nfs_exports_shares`, niet in het bestand: de volgende run zet dat toch terug.

### De vault-wachtwoorden staan ook op Semaphore

De `semaphore`-rol kopieert ze naar de Semaphore-container, zodat die zijn
geplande jobs kan draaien. Een back-up van `semaphore` (ct 104) bevat ze dus
ook. Handig als je werkstation weg is, maar bewaar ze toch apart.
