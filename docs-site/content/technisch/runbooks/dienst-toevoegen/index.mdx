# Een dienst toevoegen

Je wil iets nieuws bereikbaar maken op `naam.neodata.be`. Hoe je dat doet,
hangt af van één vraag: **wat heb je al?**

## Welk geval ben jij?

| Jouw situatie | Voorbeeld | Ga naar |
| --- | --- | --- |
| Je wil een **nieuwe app** draaien en die bestaat als Docker-image | Memos, Vaultwarden, Jellyfin | [Geval 1 — Nieuwe Docker-app](#geval-1--nieuwe-docker-app) |
| Het ding **draait al** ergens, je wil er alleen een mooi adres voor | Shelfmark op de Mac mini, Home Assistant, de webpagina van je printer | [Geval 2 — Alleen een adres](#geval-2--alleen-een-adres) |
| Je wil software **rechtstreeks op een machine** installeren, zonder Docker | AdGuard, Caddy, PBS | [Geval 3 — Eigen rol](#geval-3--eigen-rol-zonder-docker) |

Twijfel je: het is bijna altijd **geval 1**. Geval 3 heb je zelden nodig.

<Callout type="info">
Moet je dienst op een **nieuwe machine** (LXC) draaien? Bouw die dan eerst met
[Nieuwe machine](/technisch/runbooks/nieuwe-guest/). Alles hieronder gaat
ervan uit dat de machine al bestaat.
</Callout>

### Drie woorden die je nodig hebt

**Stack** — één Docker-app: een map in de `containers`-repo met een
`docker-compose.yml` en een `.env`. Alle stacks draaien op de machine `docker`.

**Route** — één regel in `caddy_sites` die zegt: "stuur `naam.neodata.be` door
naar deze machine op deze poort". Zonder route kan je de dienst alleen via zijn
IP-adres bereiken.

**Rol** — een installatierecept in `roles/` dat software direct op een machine
zet, zoals je met de hand `apt install` zou doen. Geen Docker.

## Geval 1 — Nieuwe Docker-app

<Callout type="info">
**Moet je eerst zelf een `docker-compose.yml` schrijven? Nee.** Het playbook
`new-service.yml` schrijft hem voor je. Jij geeft alleen de naam, het image en
de poort op. Daarna kijk je hem na en vul je aan wat de app extra nodig heeft.
</Callout>

We gebruiken Memos als voorbeeld.

<Steps>

### Zoek drie dingen op

Kijk in de documentatie of op de GitHub-pagina van de app. Daar staat bijna
altijd een voorbeeld-`docker-compose.yml` waar je dit uit haalt:

| Wat | Voorbeeld Memos | Waar vind je het |
| --- | --- | --- |
| **Image met versie** | `ghcr.io/usememos/memos:0.24.4` | de regel `image:` — neem een vaste versie, niet `latest` |
| **Poort** | `5230` | de regel `ports:`, het getal rechts van de `:` |
| **Datamap in de container** | `/var/opt/memos` | de regel `volumes:`, het pad rechts van de `:` |

Kies ook een **poort die nog vrij is** op `docker`. Kijk in
`inventory/host_vars/caddy/main.yml` welke al gebruikt worden. Het playbook
weigert trouwens als je een bezette kiest.

### Laat het playbook alles aanmaken

Vanuit de root van deze repo:

```bash
ansible-playbook playbooks/new-service.yml \
  -e svc_name=memos \
  -e svc_port=5230 \
  -e svc_image=ghcr.io/usememos/memos:0.24.4 \
  -e svc_volume=/var/opt/memos \
  -e '{"svc_desc": "Memos - snelle notities"}'
```

Dit maakt vijf dingen voor je:

1. `stacks/memos/docker-compose.yml` in de `containers`-repo
2. een `.env` ernaast (tijdzone, IP, datamap…)
3. een versleutelde kopie van die `.env` in `files/env/memos.env`, in deze repo
4. de stack in de lijst van `docker` (`inventory/host_vars/docker.yml`)
5. de route in `caddy_sites` (`inventory/host_vars/caddy/main.yml`)

<Callout type="warning">
Een waarde **met spaties** (zoals `svc_desc`) moet je als JSON meegeven, zoals
hierboven: `-e '{"svc_desc": "..."}'`. Schrijf je `-e 'svc_desc=a b c'`, dan
houdt Ansible alleen `a` over.
</Callout>

Extra opties, als je ze nodig hebt:

| Optie | Wanneer |
| --- | --- |
| `svc_container_port` | de app luistert binnen de container op een andere poort dan `svc_port` |
| `svc_subdomain` | het adres moet anders heten dan de stack (standaard: `svc_name`) |
| `svc_env` | extra omgevingsvariabelen, bv. `-e '{"svc_env": ["MEMOS_MODE=prod"]}'` |

### Kijk de compose-file na

```bash
$EDITOR ~/Development/containers/stacks/memos/docker-compose.yml
```

Voor een simpele app klopt hij meteen. Vergelijk hem met het voorbeeld uit de
documentatie van de app en vul aan wat ontbreekt, bijvoorbeeld:

- extra omgevingsvariabelen
- een tweede volume (bv. een map met media)
- een database-container ernaast

Heeft de app een **wachtwoord of sleutel** nodig? Zet dat niet in de
compose-file, maar in de versleutelde `.env`:

```bash
ansible-vault edit files/env/memos.env
```

en verwijs ernaar in de compose-file met `${NAAM_VAN_DE_VARIABELE}`.

<Callout type="info">
Het is die versleutelde `files/env/memos.env` die op de server terechtkomt. De
`.env` in de containers-repo is maar een lokale kopie en gaat niet mee in git.
</Callout>

### Push de containers-repo

```bash
cd ~/Development/containers
git add stacks/memos
git commit -m 'Add memos stack'
git push
```

Dit moet **vóór** de volgende stap. De server haalt de compose-file uit git,
niet van je laptop. Wat niet gepusht is, bestaat voor de server niet.

### Commit en push ook deze repo

```bash
cd ~/Development/homelab-ansible
git add inventory files/env/memos.env
git commit -m 'Memos toegevoegd'
git push
```

Semaphore draait elke nacht vanuit git. Push je dit niet, dan kent Semaphore
je nieuwe dienst niet.

### Zet hem live

```bash
ansible-playbook playbooks/stacks.yml     # start de container op docker
ansible-playbook playbooks/caddy.yml      # maakt memos.neodata.be aan
```

### Test

```bash
ansible-playbook playbooks/caddy-smoketest.yml
```

en open [memos.neodata.be](https://memos.neodata.be) in je browser.

### Werk de docs bij

```bash
ansible-playbook playbooks/docs.yml
```

De servicepagina's op deze site worden gemaakt uit `caddy_sites`. Sla je dit
over, dan werkt de dienst wel maar staat hij hier niet.

</Steps>

## Geval 2 — Alleen een adres

De dienst **draait al**, je wil hem alleen bereiken op `naam.neodata.be` in
plaats van op `192.168.0.26:8084`. Je hoeft niets te installeren. Je voegt
alleen een route toe.

Voorbeeld: Shelfmark draait op de Mac mini op poort 8084.

<Steps>

### Voeg één regel toe aan `caddy_sites`

```bash
$EDITOR inventory/host_vars/caddy/main.yml
```

Zet onder `caddy_sites:`:

```yaml
  - { name: shelfmark, host: macmini, port: 8084, desc: "Shelfmark — metadata voor boeken" }
```

- `name` — wordt het adres: `shelfmark.neodata.be`
- `host` — de naam van de machine **zoals in de inventory** (niet het IP)
- `port` — de poort waar de dienst op luistert
- `desc` — korte uitleg, komt op deze docs-site

<Callout type="info">
Staat de machine **niet** in de inventory (bv. een printer)? Gebruik dan
`upstream: "192.168.0.50:80"` in plaats van `host` en `port`.
</Callout>

### Zet hem live en test

```bash
ansible-playbook playbooks/caddy.yml
ansible-playbook playbooks/caddy-smoketest.yml
ansible-playbook playbooks/docs.yml
```

### Commit en push

```bash
git add inventory && git commit -m 'Route voor shelfmark' && git push
```

</Steps>

### Alle velden van een route

| Veld | Doet |
| --- | --- |
| `name` | wordt `name.neodata.be` |
| `host` | een **inventory-hostnaam**; zijn adres wordt de bestemming |
| `port` | de poort waar de dienst luistert |
| `upstream` | alternatief voor `host` + `port`, voor iets dat niet in de inventory staat |
| `https` | de dienst praat zelf HTTPS (met een zelfgemaakt certificaat) |
| `host_header` | stuur de oorspronkelijke `Host`-header door |
| `forwarded` | zet `X-Real-IP` en `X-Forwarded-*` erbij (Home Assistant wil dit) |
| `auth` | zet een login (tinyauth) voor de dienst |

Waarom `host` en niet gewoon een IP? Verhuist een machine naar een ander adres,
dan pas je dat op één plek aan en volgen alle routes vanzelf.

## Geval 3 — Eigen rol (zonder Docker)

Dit is voor software die je **rechtstreeks op een machine** installeert, zonder
Docker. Denk aan dingen die laag in het netwerk zitten of een eigen machine
horen te hebben: DNS (AdGuard), de reverse proxy (Caddy), de backupserver (PBS).

<Callout type="warning">
Bestaat er een Docker-image van je app? Dan wil je [geval 1](#geval-1--nieuwe-docker-app).
Een rol is meer werk: jij schrijft zelf de installatiestappen.
</Callout>

Voorbeeld: Vaultwarden op een eigen LXC.

<Steps>

### Zorg dat de machine bestaat

Maak de LXC met [Nieuwe machine](/technisch/runbooks/nieuwe-guest/).

### Laat het playbook een lege rol aanmaken

```bash
ansible-playbook playbooks/new-role.yml \
  -e svc_name=vaultwarden \
  -e svc_host=vaultwarden \
  -e svc_tag=secrets \
  -e '{"svc_desc": "Vaultwarden - wachtwoordkluis"}'
```

- `svc_name` — naam van de rol; alleen kleine letters, cijfers en `_`
- `svc_host` — op welke machine hij moet draaien
- `svc_tag` — een label om hem apart te kunnen draaien

Dit maakt `roles/vaultwarden/` en `playbooks/vaultwarden.yml`. De rol is nog
**leeg**: er staat alleen commentaar in dat uitlegt wat er moet komen.

### Schrijf de installatiestappen

```bash
$EDITOR roles/vaultwarden/tasks/main.yml
```

Volg de TODO's. Ze beschrijven het vaste patroon dat alle rollen hier volgen:

1. installeer een vaste versie
2. schrijf de configuratie (en laat die controleren vóór ze actief wordt)
3. zet de dienst aan
4. herstart hem als de configuratie verandert

Kijk bij twijfel naar een bestaande rol, zoals `roles/adguard/`.

### Zet hem in `site.yml`

```bash
$EDITOR playbooks/site.yml
```

Het playbook doet dit bewust niet zelf: de volgorde in `site.yml` telt (eerst
waar je dienst van afhangt, daarna je dienst), en dat moet jij beslissen. De
regels om te plakken staan aan het eind van de run.

### Probeer droog, dan echt

```bash
ansible-playbook playbooks/vaultwarden.yml --check --diff   # toont wat er zou veranderen
ansible-playbook playbooks/vaultwarden.yml                  # doet het echt
```

### Geef hem een adres

Volg [geval 2](#geval-2--alleen-een-adres) om een route toe te voegen.

</Steps>

## Goed om te weten

### Waarom `new-service.yml` weigert te overschrijven

Voor het iets schrijft, controleert het of de naam én de poort nog vrij zijn.
Een dubbele poort start stilletjes niet en een dubbele naam overschrijft een
bestaande dienst. Dat merk je pas na een deploy. Nu krijg je meteen een
foutmelding.

### De smoketest

```bash
ansible-playbook playbooks/caddy-smoketest.yml
```

Bezoekt elk adres uit `caddy_sites` en faalt als er één stuk is (een 5xx of
geen verbinding). Een 401 of een redirect telt niet als stuk: dat is de login
die gewoon zijn werk doet.

Hij zit niet in `site.yml` omdat hij alleen controleert en niets verandert.
Draai hem na `caddy.yml` en na `caddy-upgrade.yml`.
