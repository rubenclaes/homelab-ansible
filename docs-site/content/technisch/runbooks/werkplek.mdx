# Werkplek

Alles wat je op je laptop (`mbp`) doet om vlot met de homelab te werken:
hosts bij naam bereiken, korte shell-commando's, en veilig playbooks draaien.

## Welk geval ben jij?

| Jouw situatie | Voorbeeld | Ga naar |
| --- | --- | --- |
| Je wil `ssh caddy` kunnen typen in plaats van een IP-adres | laptop net opgezet, of `~/.zshrc` kwijt | [Geval 1 — Laptop klaarzetten](#geval-1--laptop-klaarzetten) |
| Er is een **nieuwe machine** bij en `ssh <naam>` werkt nog niet | net een LXC gebouwd met `new-guest.yml` | [Geval 2 — Nieuwe machine bij naam bereiken](#geval-2--nieuwe-machine-bij-naam-bereiken) |
| Je wil een **afkorting** toevoegen of aanpassen in je shell | een alias zoals `hl` of `ap` | [Geval 3 — Shell-afkorting aanpassen](#geval-3--shell-afkorting-aanpassen) |
| Je wil **snel iets weten** van een host, zonder in te loggen | welke Caddy-versie draait er, leven ze nog | [Geval 4 — Snel iets vragen aan een host](#geval-4--snel-iets-vragen-aan-een-host) |
| Je wil een playbook draaien, maar eerst **zien wat het doet** | `site.yml` na een wijziging in de inventory | [Geval 5 — Veilig een playbook proberen](#geval-5--veilig-een-playbook-proberen) |
| Je hebt net een playbook gedraaid: **wat nu?** | na `caddy.yml`, `update.yml`, `stacks.yml` | [Geval 6 — Na een run](#geval-6--na-een-run) |

<Callout type="info">
Nog nooit met deze repo gewerkt op deze laptop? Doe eerst
[Van niets naar alles, geval 1](/technisch/runbooks/opzetten/#geval-1--nieuwe-laptop-klaarzetten): de
`ansible`-sleutel en de vault-wachtwoorden moeten er zijn.
</Callout>

### Woorden die je nodig hebt

**Dotfiles** — je persoonlijke configbestanden (`~/.zshrc`, `~/.ssh/config`). Het playbook `dotfiles.yml` schrijft ze voor je.

**Inventory** — de lijst van alle machines, in `inventory/`. De Proxmox-guests komen automatisch uit de Proxmox-API.

**Ad-hoc-commando** — één commando op een host via `ansible`, zonder playbook.

## Geval 1 — Laptop klaarzetten

<Steps>

### Ga naar de repo

```bash
cd ~/Development/homelab-ansible
```

### Draai het dotfiles-playbook

```bash
ansible-playbook playbooks/dotfiles.yml
```

Het draait lokaal op je laptop (host `mbp`) en schrijft vier dingen:

| Wat | Waar |
| --- | --- |
| een `Host`-blok per Linux-machine | `~/.ssh/config.d/homelab` |
| één regel `Include ~/.ssh/config.d/*` bovenaan | `~/.ssh/config` |
| je shell, met de afkortingen erin | `~/.zshrc` |
| je git-instellingen (naam, e-mail, signeren) | `~/.gitconfig` |

<Callout type="warning">
Zie je de melding "`~/.ssh/config.d/homelab` niet aangeraakt"? Dan kon de
Proxmox-API niet gelezen worden. Controleer met `ansible-inventory --graph` of
de guests erin staan, en draai opnieuw. Zie
[Goed om te weten](#goed-om-te-weten).
</Callout>

### Open een nieuwe terminal

```bash
exec zsh   # of sluit en open je terminal
```

De nieuwe `~/.zshrc` telt pas in een nieuwe shell.

### Test

```bash
ssh caddy   # moet meteen binnenkomen, zonder wachtwoord
```

</Steps>

### Welke namen je nu kan gebruiken

| Typ dit | In plaats van |
| --- | --- |
| `ssh pve01` | `ssh ansible@192.168.0.14` |
| `ssh docker` | `ssh ansible@192.168.0.15` |
| `ssh docker-grafana-stack` | `ssh ansible@192.168.0.17` |
| `ssh caddy` | `ssh ansible@192.168.0.25` |
| `ssh adguard` | `ssh ansible@192.168.0.29` |
| `ssh semaphore` | `ssh ansible@192.168.0.30` |
| `ssh pbs` | `ssh ansible@192.168.0.181` |
| `ssh tailscale` | `ssh ansible@192.168.0.50` |

Dit lijstje is niet de bron: dat is de inventory, zie [Machines](/technisch/machines/).
Verhuist een host naar een ander adres, dan volgt `ssh <naam>` na de volgende run vanzelf.

`haos` en `macmini` staan er **niet** bij: ze zitten niet in de groep `linux`
(Home Assistant is een appliance, de Mac mini zit in `macs`).

### Welke afkortingen je nu hebt

| Typ dit | Doet |
| --- | --- |
| `hl` | `cd ~/Development/homelab-ansible` |
| `ap` | `ansible-playbook` |

Dus `hl && ap playbooks/site.yml` werkt vanuit elke map.

## Geval 2 — Nieuwe machine bij naam bereiken

Voorbeeld: je hebt net `vaultwarden` gebouwd met
[Nieuwe machine](/technisch/runbooks/nieuwe-guest/).

<Steps>

### Kijk of hij in de inventory staat

```bash
ansible-inventory --graph linux   # vaultwarden moet in de lijst staan
```

Staat hij er niet, dan kent Proxmox hem nog niet. Draai eerst `new-guest.yml` af.

### Draai het dotfiles-playbook

```bash
ansible-playbook playbooks/dotfiles.yml
```

### Test

```bash
ssh vaultwarden
```

</Steps>

<Callout type="warning">
De nachtelijke run in Semaphore werkt je laptop **niet** bij: "Site converge"
draait met `--limit all:!mbp:!semaphore`. Een nieuwe `ssh <naam>` krijg je
dus alleen door zelf `dotfiles.yml` (of `site.yml` zonder `--limit`) te draaien.
</Callout>

## Geval 3 — Shell-afkorting aanpassen

Voorbeeld: je wil een alias `gs` voor `git status`.

<Steps>

### Pas het blok in de inventory aan

```bash
$EDITOR inventory/host_vars/mbp.yml
```

Voeg onder `dotfiles_zsh_block: |-` een regel toe:

```yaml
  alias gs='git status'
```

### Draai het dotfiles-playbook

```bash
ansible-playbook playbooks/dotfiles.yml
```

### Laad je shell opnieuw

```bash
exec zsh
```

### Commit en push

```bash
git add inventory/host_vars/mbp.yml
git commit -m 'Alias gs toegevoegd'
git push
```

</Steps>

<Callout type="warning">
Bewerk `~/.zshrc` **niet** met de hand: de volgende run overschrijft het hele
bestand. Ansible zet de oude wel als back-up ernaast (`~/.zshrc.<datum>~`).
Wil je iets buiten het afkortingenblok veranderen, pas dan het sjabloon
`roles/dotfiles/templates/zshrc.j2` aan.
</Callout>

## Geval 4 — Snel iets vragen aan een host

Voor iets kleins hoef je niet in te loggen.

<Steps>

### Kies één host, of een hele groep

```bash
ansible caddy -a "caddy version"          # één host
ansible guests -a "uptime"                # alle guests
ansible linux -m ansible.builtin.ping     # bereik ik ze allemaal nog?
```

Het eerste woord is een hostnaam of een groep uit de inventory. Na `-a` komt
het commando.

</Steps>

Handige groepen:

| Groep | Wie |
| --- | --- |
| `linux` | alle Linux-machines, inclusief `pve01` |
| `guests` | alle Linux-guests op `pve01` |
| `docker_hosts` | `docker` en `docker-grafana-stack` |
| `macs` | `macmini` en `mbp` |

## Geval 5 — Veilig een playbook proberen

<Steps>

### Kijk wie en wat je raakt

```bash
ansible-playbook playbooks/site.yml --list-hosts   # welke hosts
ansible-playbook playbooks/site.yml --list-tags    # welke onderdelen
```

### Doe een droogloop

```bash
ansible-playbook playbooks/site.yml --check --diff   # toont wat er zou veranderen, verandert niets
```

### Beperk wat je raakt

```bash
ansible-playbook playbooks/site.yml --limit docker            # één host
ansible-playbook playbooks/site.yml --limit 'linux:!proxmox'  # alles behalve de hypervisor
ansible-playbook playbooks/site.yml --tags dns                # één onderdeel (hier: AdGuard)
```

Zet de aanhalingstekens rond `'linux:!proxmox'`, anders snapt de shell de `!` verkeerd.

### Draai het echt

Hetzelfde commando, zonder `--check --diff`.

</Steps>

## Geval 6 — Na een run

Bijna elk playbook heeft een logische volgende stap: controleren of het klopt,
of de rest laten bijtrekken.

| Draaide je | Draai dan | Waarom |
| --- | --- | --- |
| `site.yml` | `site.yml --check --diff` | een tweede keer hoort niets meer te veranderen |
| `new-guest.yml` | `site.yml --limit <host>`, daarna `dotfiles.yml` | de dienst erop, en de nieuwe `ssh <host>` |
| `caddy.yml` | `caddy-smoketest.yml` | vraagt elke route echt op, faalt op een dode |
| `stacks.yml` (nieuwe stack) | `caddy.yml`, `docs.yml` | route en servicepagina volgen de stack |
| `update.yml` | `report.yml` | de lijst met openstaande updates hoort nu leeg |
| iets in de inventory | `docs.yml` | de pagina's onder Technisch komen daaruit |
| wat dan ook, later | `drift.yml` | is er sindsdien iets met de hand gewijzigd |

`report.yml` publiceert naar [report.neodata.be](https://report.neodata.be):
de snelste blik op de hele vloot (schijf, uptime, herstarts, openstaande
updates, back-ups, route-drift). Waarom deze controle-playbooks niet in
`site.yml` zitten staat in [Onderhoud](/technisch/runbooks/onderhoud/).

## Goed om te weten

### Waar de ssh-namen vandaan komen

De dotfiles-rol loopt over de inventory-groep `linux` en schrijft per host een
blok met zijn adres, de gebruiker `ansible` en `~/.ssh/ansible_ed25519`. Niets
wordt met de hand bijgehouden: staat een host in de inventory, dan kan je hem
na één run bij naam sshen. Bewerk `~/.ssh/config.d/homelab` dus niet zelf; de
volgende run overschrijft het.

### Waarom de rol soms de ssh-config niet aanraakt

Op `pve01` na komen alle hosts uit de Proxmox-API. Is die even niet bereikbaar,
dan krijgt Ansible geen foutmelding maar een lege groep, en zou het sjabloon
een bijna lege config schrijven. Dat merk je pas de volgende dag. Daarom laat de
rol het bestand dan staan zoals het was en zegt hij dat. De rest (git, zshrc)
loopt gewoon door.

### Waarom de `Include`-regel bovenaan staat

ssh neemt de eerste waarde die hij vindt voor een host. Staat de `Include`
onderaan of binnen een ander `Host`-blok, dan kunnen je eigen regels de
homelab-regels overschaduwen of worden ze niet gelezen.

### Waarom je nooit een vault-wachtwoord moet typen

`ansible.cfg` zegt dat `bin/vault-pass-client` de wachtwoorden levert. Dat
script leest `~/.ansible/vault_pass_infra` en `~/.ansible/vault_pass_stacks`
(aangemaakt in [Van niets naar alles](/technisch/runbooks/opzetten/)). Zijn die
er niet, dan valt het terug op het oude `~/.ansible/vault_pass`, waar
`ANSIBLE_VAULT_PASSWORD_FILE` in je `~/.zshrc` ook nog naar wijst.
